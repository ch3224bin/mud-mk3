# 팀 공통 브리프 (자율 작성 모드)

모든 팀원(서브에이전트)은 작업 전에 이 파일을 읽는다.

## 목표

창호(설계자)가 큰 얼개를 잡은 룰북 `docs/spec/game-rule/` 의 세부 사항을 에이전트가 채워, 개발자가 **이 룰북만 보고 게임 규칙을 빠짐없이 구현할 수 있게** 만든다. 수치는 게임 이론상 재미를 주도록 검토한다.

## 작성 규칙 (mud-spec 스킬 규칙 + 이번 모드의 차이)

- 파일·구조 규칙은 `.claude/skills/mud-spec/SKILL.md` 를 따른다. 장 파일은 `# 장`, 절 `##`, 그 아래 `###`. 같은 장 링크 `#앵커`, 다른 장 `파일.md#앵커`.
- **룰북 범위**: 플레이어가 겪는 규칙·수치·명령어·출력. DB/서버/프로토콜/클래스 설계 같은 기술 spec 은 쓰지 않는다.
- **창호가 이미 정한 규칙은 바꾸지 않는다.** 기존 문장과 충돌하는 제안은 덮어쓰지 말고, 결과 보고에 "결정 필요" 항목으로 돌려준다(리드가 `docs/spec/review/decisions-needed.md` 에 모은다).
- 기존 `(수치는 잠정, 나중에 조절)` 수치는 창호가 정한 것이다. 그대로 두고 그 위에 쌓는다. 그 수치가 게임성에 문제가 있으면 바꾸지 말고 "결정 필요"로 돌려준다.
- **에이전트가 새로 정한 규칙·수치는 그 문장 끝에 `(제안)` 을 붙인다.** 창호가 나중에 골라 검토한다. 표로 정했으면 표 바로 위·아래 문장이나 표 제목 줄 끝에 `(제안)` 을 붙인다.
- `> 미정: ...` 을 채웠으면 그 미정 줄을 지우고 본문 문장으로 바꾼다. 일부만 채웠으면 남은 것만 미정으로 남긴다.
- 창호의 용어와 문장 결을 따른다(짧은 평서문, "~다"). 원작(범인수선전/학사신공) 용어를 쓰되 원작 설정을 길게 옮기지 않는다.
- **콘텐츠 목록 vs 규칙**: 모든 공법·몹·아이템을 다 나열할 필요는 없다. 대신 (1) 콘텐츠가 가져야 할 속성과 경지·등급별 값의 범위·공식(콘텐츠 제작 규칙), (2) 첫 지역(연기기)에서 실제로 쓸 시작 콘텐츠 몇 개를 정한다. 그러면 개발자가 MVP 를 구현하고, 이후 콘텐츠는 규칙에 맞춰 추가할 수 있다.
- **구현 충분성**: 모든 공식·수치·경계 조건(0·최대치·동시 발생·실패), 상태 전이(언제 시작·끝나는지), 명령어의 입력 형태와 출력(성공·실패 메시지 예시)이 정의돼야 한다.
- 수치는 기존 기준과 맞춘다: 틱 = 1초, 공통 대기시간 1.5초, 같은 경지 1대1 주력 신통 6~8발, 낮은 경지 1대1 20~30초. 페이싱·경제 기준은 `docs/spec/review/design-baseline.md` (있으면) 를 따른다.
- 원작 조사는 꼭 필요할 때만, 짧게.

## 공유 파일 다루기

- `docs/spec/glossary.md`, `docs/spec/game-rule/index.md`, `docs/spec/review/decisions-needed.md`, `docs/spec/review/progress.md` 는 **리드만 고친다.** 팀원은 바꿀 내용을 결과 보고에 적어 돌려준다(용어집 줄, 열린 질문 추가·삭제, 결정 필요 항목).
- 팀원은 자기에게 맡겨진 파일만 고친다. 다른 장에 필요한 변경은 결과 보고의 "다른 장에 필요한 것" 에 적는다.
- git commit/push 는 하지 않는다(리드가 한다).

## 결과 보고 형식 (끝나면 이 형식으로 반환하고 종료)

```
## 한 일 (5줄 이내)
## 용어집 갱신 (용어 | 게임 정의 요지) — 없으면 생략
## index 열린 질문 (삭제/추가) — 없으면 생략
## 결정 필요 (창호 판단: 기존 규칙과 충돌·기존 잠정 수치 문제) — 없으면 생략
## 다른 장에 필요한 것 — 없으면 생략
```

보고는 짧게(전체 60줄 이내). 자세한 내용은 문서와 리뷰 파일에 있다.
