# 관리 툴

머드 게임 관리 화면. → [목차](index.md)

- 관리 툴은 `admin-console` 모듈로, 플레이 화면(`play-client`)과 분리된 Next.js 앱이다. `world-server` 와 REST로 통신한다. → [플랫폼: 저장소 구성](platform.md#저장소-구성)
- 관리 툴은 Google 로그인으로 들어오고, 서버 설정에 적힌 관리자 Google 이메일 목록에 있는 계정만 쓸 수 있다. → [인증](auth.md#관리자)

## 데이터 주도 콘텐츠

- 시스템(엔진 코드)은 틀을 만든다. 그 틀에 담기는 내용은 관리 툴에서 입력받는다.
  - 예: "NPC가 대사를 한다"는 틀은 엔진이, 어떤 NPC가 어떤 대사를 하는지는 관리 툴에서 입력한 데이터가 정한다.
- 하드 코딩은 최대한 피한다. 다만 어쩔 수 없이 하드 코딩이 필요한 경우도 있을 것으로 보이며, 무조건 관리 툴로 다루는 것은 아니다.
- 당장 해볼 수 있는 것은 관리 툴로 만들고, 이벤트처럼 애매한 부분은 코딩한다. → [이벤트 · 시나리오](event.md)
- 어디까지가 엔진이고 어디부터가 데이터인지는 시스템마다 문서에서 정한다. 아직 정하지 않은 경계는 각 문서의 열린 질문에 남긴다.

## 1차 화면

admin-console은 정적 export이고, 경로는 쿼리스트링으로 id를 받는다. (제안)

- `/` 로그인: `Google로 로그인` 버튼(= `${worldServerUrl}/api/auth/login?client=admin` 으로 이동), 개발용 로그인 폼, `?loginError=1` 이면 `로그인하지 못했습니다. 다시 시도하십시오.`. 로그인 뒤 관리자가 아니면 `관리자만 쓸 수 있습니다.` 와 로그아웃 버튼을 보인다. → [인증](auth.md#1차-로그인-흐름) (제안)
- `/zones/` 지역 목록(이름·방 수), 지역 만들기 폼, 지역마다 수정·삭제. (제안)
- `/zone/?id=1` 지역 하나: 방 목록(이름·출구 수, 시작 방 표시)과 방 만들기 폼. (제안)
- `/room/?id=3` 방 하나: 이름·묘사·지역 수정, 삭제, `시작 방으로 지정` 버튼, 출구 표(방위·대상 방(지역)·삭제), 출구 추가 폼(방위 선택 → 대상 지역 선택 → 대상 방 선택, `반대 방향도` 체크박스 기본 켜짐). (제안)
- 위쪽 공통 바: 현재 시작 방, 지역 목록 링크, 로그아웃. (제안)

## 1차 REST API

모두 `/api/admin/**` 이고 `ADMIN` 권한이 필요하다(로그인 안 됨 401, 관리자 아님 403). 변경 요청에는 헤더 `X-MUD-Client: 1` 이 있어야 한다. → [인증](auth.md#오리진corscsrf) 오류는 `ProblemDetail`(`title`, `status`, `detail`=한국어 메시지, `timestamp`, `exception`)이다. 검증 실패·잘못된 값·없는 id는 400, 이름 중복·규칙 충돌은 409다. (제안)

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `GET /api/admin/zones` | — | 200 `ZoneResponse[]`(이름순) |
| `POST /api/admin/zones` | `{name, description}` | 201 `ZoneResponse` |
| `PUT /api/admin/zones/{zoneId}` | `{name, description}` | 200 `ZoneResponse` |
| `DELETE /api/admin/zones/{zoneId}` | — | 204. 방이 있으면 409 |
| `GET /api/admin/zones/{zoneId}/rooms` | — | 200 `RoomSummaryResponse[]`(id순) |
| `POST /api/admin/rooms` | `{zoneId, name, description}` | 201 `RoomDetailResponse` |
| `GET /api/admin/rooms/{roomId}` | — | 200 `RoomDetailResponse` |
| `PUT /api/admin/rooms/{roomId}` | `{zoneId, name, description}` | 200 `RoomDetailResponse` |
| `DELETE /api/admin/rooms/{roomId}` | — | 204. 이 방으로 오는 출구도 지운다. 시작 방이면 409 |
| `PUT /api/admin/rooms/{roomId}/exits/{direction}` | `{targetRoomId, twoWay}` | 200 `RoomDetailResponse` |
| `DELETE /api/admin/rooms/{roomId}/exits/{direction}?twoWay=true` | — | 204. `twoWay` 기본값은 false |
| `GET /api/admin/world` | — | 200 `WorldResponse` |
| `PUT /api/admin/world/start-room` | `{roomId}` | 200 `WorldResponse` |

- 응답 모양 (제안): `ZoneResponse {id, name, description, roomCount}`, `RoomSummaryResponse {id, name, exitCount}`, `RoomDetailResponse {id, zoneId, zoneName, name, description, start, exits: [{direction, directionName, targetRoomId, targetRoomName, targetZoneName}]}`(exits는 방위 순서), `WorldResponse {startRoomId, startRoomName, startZoneName}`(시작 방이 없으면 셋 다 null).
- `{direction}` 경로 값은 `EAST WEST SOUTH NORTH NORTHEAST NORTHWEST SOUTHEAST SOUTHWEST UP DOWN` 이다. (제안)

### 출구 만들기·지우기 규칙

- 반대 방향 출구 자동 생성: `twoWay=true` 면 대상 방에 반대 방위 출구를 같이 만든다. 대상 방의 반대 방위 출구가 이미 이 방을 가리키면 그대로 두고, 다른 방을 가리키면 아무것도 바꾸지 않고 409다. admin-console은 폼의 `반대 방향도` 체크(기본 켜짐)를 따라 `twoWay` 를 보낸다. (제안)
- 출구 삭제에서 `twoWay=true` 면 대상 방의 반대 출구가 이 방을 가리킬 때만 같이 지운다. (제안)
- 출구의 대상을 바꿔도 옛 대상 방의 반대 출구는 그대로 남는다. (제안)
- 없는 방위의 출구를 지우는 요청은 아무것도 하지 않고 204다. (제안)

### 관리 툴 변경의 반영

- 맵(지역·방·출구)의 변경은 실행 중인 게임에 바로 반영된다. 게임이 맵을 캐시하지 않고 명령마다 DB에서 읽기 때문이다. → [플랫폼: 1차 월드 상태와 저장](platform.md#1차-월드-상태와-저장) (제안)
- 플레이어가 서 있는 방을 지우면 그 플레이어는 시작 방으로 옮겨진다. (제안)
- 2차의 성·종문·지역 소유·NPC(대사·배치) 변경도 맵처럼 실행 중인 게임에 바로 반영된다. 게임이 명령마다 DB에서 읽기 때문이다. 방 머리 소유와 방의 NPC는 다음 방 보기부터 바뀌고, 같은 방 사람에게 따로 알리지 않는다. (제안)
- 2차 스키마도 1차처럼 `ddl-auto=update` 로 새 테이블(`faction`, `npc`, `npc_topic`)과 `zone.owner_id` 열이 생긴다. 마이그레이션 도구는 여전히 없다. (제안)
- 3차의 아이템 종류·방 바닥 배치·시작 소지품·NPC 상점 역할 변경도 바로 반영된다. 게임이 명령마다 DB에서 읽기 때문이다. 바닥은 다음 방 보기부터, 시작 소지품은 그 뒤에 만드는 캐릭터부터, 상점은 다음 상점 명령부터 바뀌고, 같은 방 사람에게 따로 알리지 않는다. (제안)
- **쓰이는 아이템 종류 지우기·바꾸기:** 어딘가에 쓰이는 물건(누군가의 소지품, 바닥 배치, 사라지지 않은 버린 물건, 상점, 시작 소지품 어디든)은 지울 수 없고(409), 종류와 저물대 등급을 바꿀 수 없다(409 — 칸 계산이 바뀌어 소지품이 칸을 넘는 일을 막는다). 이름·묘사·기준가는 바꿀 수 있고, 기준가를 바꿀 때는 상점 값 검사를 한다([NPC: 3차 상점 역할 데이터](npc.md#3차-상점-역할-데이터)). 지울 때 사라질 시각이 지난 버린 물건 행은 먼저 지운다. (제안)
- 4차의 공법·신통 정의와 옥간·서책의 담긴 공법 변경도 바로 반영된다. 배운 신통·공법 단계 몫 스탯은 저장하지 않고 명령마다 정의에서 계산하므로, 익힌 캐릭터에게도 다음 명령부터 바뀐 정의(신통 추가·삭제, 스탯 증가)가 보인다. 따로 알리지 않는다. 관리 툴 경지 지정은 커밋 뒤(AFTER_COMMIT) 접속 중인 그 캐릭터에게만 알린다 → [명령어 처리: 경지가 바뀔 때](command.md#경지가-바뀔-때). 4차 스키마와 기존 캐릭터 채우기는 [플랫폼: 4차 월드 상태와 저장](platform.md#4차-월드-상태와-저장)에 있다. (제안)
- 3차 스키마도 `ddl-auto=update` 로 생긴다: `item_type`, `inventory`, `inventory_entry`, `floor_placement`, `dropped_item`, `npc_shop_item`, `world_starting_item` 과 `npc.shop_kind` 열. 마이그레이션 도구는 여전히 없다. 3차 뒤에 `귀속`·`거래 가능` 이 삭제되어 엔티티에서 열을 뺐다. `귀속`·`거래 가능` 삭제는 창호의 결정(2026-11-14)이다. 이미 만들어진 DB(pgdata)는 서버가 뜰 때 옛 열(`item_type.tradable`, 소지품 표의 귀속 열)을 합치고 지운다. 한 트랜잭션에서, 같은 (캐릭터, 종류) 행이 둘 이상이면 수를 더해 가장 작은 id 행 하나로 합치고(표시 순서 유지), 옛 유니크 제약과 옛 열을 지운다. 영석 심기보다 먼저 한다. 옛 열을 남겨 두면 NOT NULL·기본값 없는 열 때문에 새 행 저장이 깨지므로 남기지 않는다. H2(테스트)·PostgreSQL 둘 다 동작해야 한다. (제안) → [플랫폼: 저장소 구성](platform.md#저장소-구성) (제안)

## 2차 화면

1차 화면에 더한다. (제안)

- 위쪽 공통 바: `지역 목록` 옆에 `성·종문`, `NPC` 링크. (제안)
- `/factions/` 성·종문 목록(종류·이름·소유 지역 수·수정·삭제)과 `성·종문 만들기` 폼(종류 선택 `성`/`종문`, 이름, 묘사). 삭제 확인은 `'청석성' 성을(를) 지울까요?`. (제안)
- `/zones/` 지역 만들기·수정 폼에 `소유` 선택(`없음` + 성·종문 목록, 예 `청석성 (성)`), 지역 목록에 `소유` 열(없으면 `-`). (제안)
- `/npcs/` NPC 목록(이름·배치(`청우촌 / 마을 어귀` 또는 `배치 안 됨`)·낱말 수·LLM(`켬`/`끔`))과 `NPC 만들기` 링크(`/npc/`). (제안)
- `/npc/` (id 없음 = 새로 만들기, `/npc/?id=4` = 고치기): 이름, 인사말, 기본 대답(새 NPC 기본값 `글쎄, 잘 모르겠구려.`), 낱말 표(낱말·대답·`삭제`)와 `낱말 추가` 버튼(낱말과 대답이 둘 다 빈 행은 저장할 때 뺀다), `LLM 대화` 체크박스(기본 꺼짐)와 안내 `켜 두어도 지금은 정해진 대사로 답합니다.`, 배치(지역 선택 → 방 선택. 지역 선택의 첫 항목 `배치 안 함`, 방 선택의 첫 항목 `방 선택`. 지역만 고르고 방을 고르지 않으면 배치 안 함으로 저장), `저장`, 고칠 때 `삭제`(확인 `'왕씨' NPC를 지울까요?`). 만들기에 성공하면 `/npc/?id=<새 id>` 로 간다. 저장 전 클라이언트 검사는 하지 않고 서버의 `detail` 을 보인다. (제안)
- `/room/?id=` 방 화면에 `이 방의 NPC` 목록(이름 링크 → `/npc/?id=`, 없으면 `없음`). (제안)

## 2차 REST API

1차 REST API 규칙(경로·권한·`X-MUD-Client`·`ProblemDetail`·400/409 구분)을 그대로 따른다. (제안)

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `GET /api/admin/factions` | — | 200 `FactionResponse[]`(종류 성 → 종문, 같은 종류는 이름순) |
| `POST /api/admin/factions` | `{kind, name, description}` | 201 `FactionResponse` |
| `PUT /api/admin/factions/{factionId}` | `{kind, name, description}` | 200 `FactionResponse` |
| `DELETE /api/admin/factions/{factionId}` | — | 204. 소유 지역이 있으면 409 |
| `POST /api/admin/zones`, `PUT /api/admin/zones/{zoneId}` | 1차 `{name, description}` + `ownerId`(number \| null, 빠지면 null = 소유 없음) | 1차와 같음 |
| `GET /api/admin/npcs` | — | 200 `NpcSummaryResponse[]`(이름순) |
| `POST /api/admin/npcs` | `NpcSaveRequest` | 201 `NpcDetailResponse` |
| `GET /api/admin/npcs/{npcId}` | — | 200 `NpcDetailResponse` |
| `PUT /api/admin/npcs/{npcId}` | `NpcSaveRequest`(낱말 목록은 통째로 바꿈) | 200 `NpcDetailResponse` |
| `DELETE /api/admin/npcs/{npcId}` | — | 204 |

- `kind` 값은 `CASTLE` \| `SECT` 다. 그 밖의 값은 400이고 `detail` 은 공통 문구 `요청 본문을 읽을 수 없습니다` 다. (제안)
- 응답 모양 (제안):
  - `FactionResponse {id, kind, kindName, name, description, zoneCount}` — `kindName` 은 `성`·`종문`.
  - `ZoneResponse` 에 `ownerId, ownerName, ownerKind`(`CASTLE`·`SECT`)를 더한다. 소유가 없으면 셋 다 null.
  - `NpcSummaryResponse {id, name, llmEnabled, topicCount, roomId, roomName, zoneName}` — 배치 안 됐으면 room·zone 셋 다 null.
  - `NpcDetailResponse {id, name, greeting, defaultAnswer, topics: [{word, answer}], llmEnabled, roomId, roomName, zoneId, zoneName}` — `topics` 는 입력 순서.
  - `RoomDetailResponse` 에 `npcs: [{id, name}]`(그 방에 배치된 NPC, 만든 순서)를 더한다.
- `NpcSaveRequest {name, greeting, defaultAnswer, topics: [{word, answer}], llmEnabled, roomId}` — `roomId` 가 null이면 배치 안 함, `topics` 가 빠지면 빈 목록. `llmEnabled` 는 꼭 보내야 한다(빠지면 400 `요청 본문을 읽을 수 없습니다`). admin-console은 늘 보낸다. 값 규칙은 [NPC: 2차 데이터 모델](npc.md#2차-데이터-모델)을 따른다. (제안)
- 예외 문구 (제안):

| 경우 | 상태 | `detail` |
|---|---|---|
| 성·종문 이름 중복 | 409 | `이미 있는 성·종문 이름입니다: 청석성` |
| 소유 지역이 있는 성·종문 삭제 | 409 | `소유한 지역이 있는 성·종문은 지울 수 없습니다` |
| 없는 성·종문(`factionId`, 지역의 `ownerId`) | 400 | `성·종문을 찾을 수 없습니다. id: 9` |
| NPC 이름 중복(영문 대소문자 무시) | 409 | `이미 있는 NPC 이름입니다: 왕씨` |
| 한 NPC 안의 같은 낱말 | 400 | `같은 낱말이 두 번 있습니다: 단약` |
| 없는 NPC | 400 | `NPC를 찾을 수 없습니다. id: 9` |
| 없는 배치 방 | 400 | `방을 찾을 수 없습니다. id: 9`(1차 문구) |

## 3차 아이템 데이터

계획 D32~D35·D38에서 정했다. 룰북 규칙·수치는 그대로 따르고, 룰북이 정하지 않은 것만 (제안)이다. → [룰북: 아이템](../game-rule/item.md)

### 아이템 종류 `ItemType`

- 이름: 앞뒤 공백을 자르고 여러 공백은 하나로 본 뒤 1~20자, 띄어쓰기를 허용한다(`늑대 가죽`). **아이템 종류끼리 유일**(영문 대소문자 무시). 금지: 영석 등급 낱말 그대로(`하품` `중품` `상품` `극품`), 마지막 낱말이 수(`^\d+$`)이거나 `전부`, `^\d+\.` 으로 시작하는 이름. 명령 문법(마지막 낱말이 수면 수량, `전부`, 번호 `2.가죽`)이 이름과 헷갈리지 않게 하려는 것이다. → [룰북: 입력 문법](../game-rule/commands.md#입력-문법) (제안)
- 묘사 0~500자, 종류(아래 표), 기준가 0~100,000,000(하품 기준, 룰북 공통 속성), 저물대 등급(종류가 저물대일 때만 필수: 하급 20칸·중급 40칸·상급 80칸). 겹침은 입력받지 않고 종류로 정한다. (제안)
- **품질과 필요 경지는 3차에 없다.** 3차 물건은 모두 하계로 본다(이름 앞에 품질을 붙이지 않음, 판매가 배율 ×1, 매입 배율 ×1.0). 품질이 있는 물건을 얻는 길(제작·드롭·비경·거래)이 3차에 없고 상점은 하계를 팔기 때문이다. 필요 경지는 모자라도 가지고 다니고 거래할 수 있어 3차 동작에 영향이 없다. 둘 다 경지·제작이 생길 때 더한다. → [룰북: 품질](../game-rule/item.md#품질) (제안)
- **개체마다 다른 값은 3차에 없다.** 같은 종류는 한 묶음이다(귀속 구분은 삭제됨, 창호, 2026-11-14). 법기 내구도·숙련도는 법기 사용이 생길 때 더한다. → [플랫폼: 3차 월드 상태와 저장](platform.md#3차-월드-상태와-저장) (제안)

### 영석

- 영석은 별도 잔액이 아니라 **소지품 칸을 차지하는 일반 물건**이다(룰북: 같은 등급끼리 10,000개). 그래서 바닥·소지품·주기·버리기를 다른 물건과 같은 코드로 다룬다. → [룰북: 영석](../game-rule/item.md#영석) (제안)
- **영석은 엔진이 심는 아이템 종류 4개**다. 서버가 뜰 때(`ApplicationReadyEvent`) 없으면 만든다: `하품 영석`(기준가 1), `중품 영석`(100), `상품 영석`(10,000), `극품 영석`(1,000,000). 종류 `SPIRIT_STONE`, 열 `spirit_stone_grade`(유일)로 등급을 안다. 빈 DB 첫 기동 직후 아주 짧은 틈은 받아들인다. 등급끼리 저절로 바뀌지 않는다. (제안)
- 영석 묘사(글자 그대로, 룰북에 아직 없음): 하품 `영기가 옅게 서린 돌. 수선자들이 값을 치르는 데 쓴다.` / 중품 `영기가 또렷하게 서린 돌. 하품 영석 100개의 값이다.` / 상품 `영기가 짙게 서린 돌. 하품 영석 10,000개의 값이다.` / 극품 `영기가 넘실대는 돌. 하품 영석 1,000,000개의 값이다.` (제안)
- 관리 툴로 만들거나 고치거나 지울 수 없다(409 `영석은 엔진이 정한 물건이라 고치거나 지울 수 없습니다.`, 종류 `SPIRIT_STONE` 으로 만들기 400 `영석 종류는 만들 수 없습니다.`). 바닥 배치·시작 소지품에는 쓸 수 있다. 상점은 팔지도 사지도 않는다. (제안)
- 결제 규칙은 [명령어 처리: 결제와 `확인`](command.md#결제와-확인)에 있다.

### 시작 소지품 `WorldSettings.startingItems`

- `[{itemTypeId, count}]`(입력 순서, 30줄까지)를 관리 툴에서 통째로 바꾼다. 새 캐릭터를 만드는 트랜잭션에서 그 순서대로 소지품에 넣는다. 바꾼 시작 소지품은 그 뒤에 만드는 캐릭터부터 받는다. (제안)
- 저장할 때 검사(400): 같은 물건 두 번 `같은 물건이 두 번 있습니다: 회춘단`, 수 1~999,999, 저물대 4개 이상 `저물대는 세 개까지만 찰 수 있습니다.`, 칸 넘침 `시작 소지품이 칸을 넘습니다. (필요 25칸, 칸 22)`, 없는 물건 `물건 종류를 찾을 수 없습니다. id: 9`. 칸 검사는 목록을 다 넣은 뒤 한 번만 한다(저물대가 목록 뒤에 있어도 들어간다). (제안)
- 룰북의 시작 소지품(하급 저물대 1, 영수대 1, 하품 영석 30, 회춘단(연기 초) 3, 회기단(연기 초) 3)은 관리자가 넣는 콘텐츠다. **영수대는 3차에 넣지 않는다**(영수 시스템이 없고 종류 표에도 없다 — 영수가 생길 때 더한다). → [룰북: 시작 소지품](../game-rule/item.md#시작-소지품) (제안)
- 2차 이전에 만든 캐릭터는 소지품이 없으므로 처음 볼 때 빈 소지품(기본 2칸)으로 시작한다(시작 소지품을 주지 않는다). (제안)

## 3차 화면

1·2차 화면에 더한다. 저장 전 클라이언트 검사는 하지 않고 서버 `detail` 을 보인다(1·2차 관례). (제안)

- 위쪽 공통 바: `NPC` 옆에 `아이템`, `시작 소지품` 링크. (제안)
- `/items/` 아이템 목록(이름·종류·기준가·겹침(저물대는 `{n}칸`))과 `아이템 만들기` 링크(`/item/`). 수는 쉼표를 넣어 보인다(`10,000`). (제안)
- `/item/` (id 없음 = 새로, `/item/?id=7` = 고치기): `이름`, `종류`(영석 빼고), `저물대 등급`(종류가 저물대일 때만: `하급 (20칸)`·`중급 (40칸)`·`상급 (80칸)`), `묘사`(textarea), `기준가 (하품)`(기본 0), `저장`, 고칠 때 `삭제`(확인 `'회춘단' 아이템을 지울까요?`). 만들기에 성공하면 `/item/?id=<새 id>` 로 간다. **영석이면 모든 칸이 읽기 전용(disabled)이고 `저장`·`삭제` 버튼을 숨기며** `영석은 엔진이 정한 물건이라 고칠 수 없습니다.` 를 보인다(영석일 때만 종류 선택에 `영석` 이 보인다). (제안)
- `/start-items/` 시작 소지품: 행마다 `물건`(선택)·`수`·`삭제`, `물건 추가`(새 행은 목록 첫 물건(하품 영석)·수 1), `저장`, 안내 `새로 만드는 캐릭터부터 받습니다.`, 저장 성공 `저장했습니다.`, 빈 목록 `시작 소지품이 없습니다.`. (제안)
- `/room/?id=` 방 화면에 `바닥 물건` 절: 표(`물건`·`수`·`남은 수`·`재등장`(`10분` 또는 `한 번뿐`)·`수정`·`삭제`), 두기 폼(`물건`·`수`(기본 1)·`재등장(분)`(기본 10, 비우면 한 번뿐)·`바닥에 두기`), 없으면 `없음`. `수정` 은 그 행을 칸(물건·수·재등장(분))으로 바꾸고 `저장`·`취소` 버튼을 둔다(고치는 동안 두기 폼은 숨김). `삭제` 는 확인 없이 바로 지운다. (제안)
- `/npc/?id=` 에 `상점` 절(고칠 때만): `상점 종류`(`상점 아님` + 7종), 파는 물건 표(`물건` — 그 종류가 파는 종류의 물건만, `값 (하품)` — 빈칸 자리 표시 `기준가 {n}`, `삭제`), `물건 추가`, `상점 저장`(`상점 아님` 이면 상점을 없앰, 그때는 물건 표·`물건 추가` 를 숨김), 안내 `값을 비워 두면 기준가로 팝니다. 사 주는 값은 룰북 매입 규칙으로 정해집니다.`. 저장 성공은 `저장했습니다.`. 종류를 바꿔 이제 팔 수 없게 된 물건은 그 행 선택에 남겨 두고 서버 400 을 보인다. 매입가와 실제 판매가(`effectivePrice`)는 화면에 보이지 않는다. `/npcs/` 목록에 `상점` 열(종류 이름 또는 `-`). (제안)

- 요청·응답 모양 (제안):
  - `ItemTypeSaveRequest {name, description, category, baseValue, bagGrade}` — `category`·`bagGrade` 는 enum 이름, `bagGrade` 는 저물대만 값이 있고 나머지는 null.
  - `ItemTypeResponse {id, name, description, category, categoryName, stackSize, baseValue, bagGrade, bagGradeName, bagSlots, spiritStone, buyRatePercent}` — `stackSize` 는 저물대 0, `bagSlots` 는 저물대 밖 0, `buyRatePercent` 는 사지 않으면 0.
  - `FloorPlacementSaveRequest {itemTypeId, count, respawnMinutes}`(`respawnMinutes` null = 한 번뿐). `FloorPlacementResponse {id, roomId, itemTypeId, itemName, count, respawnMinutes, remaining}` — `remaining` 은 지금 시각으로 계산한 남은 수이고 저장하지 않는다.
  - `StartingItemResponse {itemTypeId, itemName, count}`.
  - `ShopSaveRequest {kind, items: [{itemTypeId, price}]}`(`price` null = 계산값). `NpcDetailResponse` 에 `shop: {kind, kindName, items: [{itemTypeId, itemName, price, effectivePrice}]} | null`, `NpcSummaryResponse` 에 `shopKindName`(없으면 null)을 더한다.
  - 바닥 배치 값: 수 1~9,999, 재등장 1~1,440분 또는 없음. 영석 종류는 바닥 배치·시작 소지품에 쓸 수 있다.
- 예외 문구 (제안):

| 경우 | 상태 | `detail` |
|---|---|---|
| 아이템 이름 중복 | 409 | `이미 있는 물건 이름입니다: 회춘단` |
| 없는 아이템 종류 | 400 | `물건 종류를 찾을 수 없습니다. id: 9` |
| 쓰이는 물건 삭제 | 409 | `쓰이는 물건은 지울 수 없습니다: 회춘단` |
| 쓰이는 물건의 종류·저물대 등급 바꾸기 | 409 | `쓰이는 물건은 종류·저물대 등급을 바꿀 수 없습니다: 회춘단` |
| 영석 고치기·지우기 | 409 | `영석은 엔진이 정한 물건이라 고치거나 지울 수 없습니다.` |
| 영석 종류로 만들기 | 400 | `영석 종류는 만들 수 없습니다.` |
| 없는 바닥 배치 | 400 | `바닥 물건을 찾을 수 없습니다. id: 9` |
| 시작 소지품 검사 | 400 | `같은 물건이 두 번 있습니다: 회춘단` · `저물대는 세 개까지만 찰 수 있습니다.` · `시작 소지품이 칸을 넘습니다. (필요 25칸, 칸 22)` |
| 상점 저장 검사·기준가 변경 409 | 400·409 | [NPC: 3차 상점 역할 데이터](npc.md#3차-상점-역할-데이터)의 문구 |
| DB 제약 위반(드문 동시 변경) | 409 | `다른 곳에서 함께 바꾸고 있어 저장하지 못했습니다. 다시 시도하십시오.` |

- 잘못된 enum 값은 2차와 같은 공통 400 `요청 본문을 읽을 수 없습니다` 다. 영석에 형식이 틀린 `PUT` 은 영석 409 보다 요청 검증 400 이 먼저다. (제안)
- DB 제약 위반(`DataIntegrityViolationException`)은 전역으로 409 고정 문구(DB 메시지는 내보내지 않고 warn 로그)다. 쓰이는 아이템 종류 지우기 경합은 FK 가 막고 이 409 가 된다. 2차까지 500 이던 드문 경합(예: 성 삭제와 지역 소유, NPC 이름 대소문자)도 DB 제약 위반으로 나면 이제 409 일 수 있다. (제안)

## 4차 범위

4차(경지·스탯·공법 배우기)에 관리 툴에서 하는 일이다. 범위는 고나가 창호 원문을 해석한 것이고 창호 확인 전이다. → [이터레이션 계획: 4차 범위](index.md#4차-범위-경지스탯--임의-경지-상승--공법신통-배우기). 아래 4차 절 전체가 (제안)이다.

- **공법·신통 정의:** 공법과 그 신통을 만들고 고치고 지운다. → [4차 데이터](#4차-데이터), [룰북: 공법 콘텐츠 제작 규칙](../game-rule/technique.md#공법-콘텐츠-제작-규칙)
- **옥간·서책에 공법 담기:** 옥간·서책 아이템 종류에 담긴 공법을 지정한다. → [옥간·서책의 담긴 공법](#옥간서책의-담긴-공법)
- **저물탁:** 아이템 종류에 저물탁 등급을 더한다. → [저물탁](#저물탁)
- **캐릭터 경지 지정(임의 경지 상승):** 캐릭터 목록을 보고, 캐릭터의 경지를 수위·돌파 없이 바로 지정한다. 게임 안 관리자 명령은 두지 않는다(관리 툴로 충분하고, 게임 명령에 권한 검사를 새로 넣지 않는다). → [4차 화면](#4차-화면)

## 4차 데이터

룰북 [공법이 가지는 것](../game-rule/technique.md#공법이-가지는-것)·[신통이 가지는 것](../game-rule/technique.md#신통이-가지는-것) 가운데 4차의 배우기·보기에 쓰는 것만 둔다. 룰북 규칙은 그대로 따르고 정하지 않은 것만 (제안)이다. 경지 코드와 경지 몫 스탯은 엔진 상수다 → [플랫폼: 4차 월드 상태와 저장](platform.md#4차-월드-상태와-저장).

### 공법 `Technique`

- 이름: 앞뒤 공백을 자른 뒤 띄어쓰기 없이 1~12자, **공법끼리 유일**(영문 대소문자 무시). `참오 장춘공` 처럼 명령 인자로 쓰이기 때문이다. (제안)
- 묘사 0~500자. (제안)
- 속성: 오행(`METAL` 금 · `WOOD` 목 · `WATER` 수 · `FIRE` 화 · `EARTH` 토) 0~5개. 비면 연체술 계열, 하나라도 있으면 오행공법 계열이다(룰북 [스탯 분류](../game-rule/stats.md#스탯-분류)). 계열은 저장하지 않고 속성으로 정한다. (제안)
- 시작 경지: 경지 코드 하나(범인 ~ 축기 대원만). 시작 경지가 범인인 공법이 입문 공법이다(룰북 [경지대별 기준값](../game-rule/technique.md#경지대별-기준값)). (제안)
- 단계 수 1~12(룰북 기준값의 최대 12). 단계 표의 행 수와 같다. (제안)
- 단계 표 `TechniqueStage`(1성부터 차례로):
  - **필요 깨달음**: 그 단계에 오르는 데 쓰는 깨달음의 합. 1성은 읽으면 이르므로 0이다(룰북). 2성부터 1~100,000,000 정수. 여러 속성이면 룰북 기본대로 속성 수로 똑같이 나누며, 나누어떨어져야 한다. 속성마다 다른 양은 `참오` 가 생길 때 더한다. (제안)
  - **영근 자질 조건**: 0~1,000 정수. 공법 속성의 영근마다 같은 값으로 확인한다(0 이면 영근만 있으면 됨). 연체술은 0이어야 한다(룰북: 조건 없음). 1성 값이 익히는 조건이다(룰북). (제안)
  - **스탯 증가**: 법력·의식·영력·정혈·육신·근력 0~10,000 정수, 영근 자질 0~100 정수(공법 속성 영근 모두에 더함). 육신·근력은 연체술 공법만, 영근 자질은 오행공법만 올린다(룰북 [육신](../game-rule/stats.md#육신)·[근력](../game-rule/stats.md#근력)). 법력 증가는 법력 최대치의 다른 보너스로 들어간다(룰북 [법력](../game-rule/stats.md#법력)). (제안)
- **4차에 없는 항목:** 수위(주는지·계수·단계별 '수위가 쌓이는 마지막 경지'), 잔본(장 수·구간), 충돌, 얻는 곳. `참오`·잔본·산공이 생길 때 더한다. 룰북의 콘텐츠 기준값(스탯 합 상한 등)은 콘텐츠를 만드는 사람이 지키고 관리 툴은 검사하지 않는다. (제안)

### 신통 `Ability`

신통은 **공법 하나에 딸린다**(룰북: 공법에서 파생된 신통). 같은 이름의 신통이 공법마다 속성이 다를 수 있기 때문이다(룰북 경신술: 속성은 공법 속성). 정의 순서가 `신통` 목록 순서다. (제안)

- 이름: 띄어쓰기 없이 1~12자, **한 공법 안에서 유일**. 다른 공법의 신통과는 같아도 된다. 룰북 [명령어](../game-rule/commands.md)에 있는 모든 명령어·줄임말·방위 이름(엔진의 예약어 목록, 첫 낱말 기준: `상태` `ㅅ` `명상` `참오` `돌파` `복용` `영석` `탐지` `도주` `막기` `추격` `대상` `중지` `확인` `동` `e` …)과 같으면 안 된다. 4차에 아직 없는 명령도 포함한다(그 명령이 생기는 순간 신통을 쓸 수 없게 되지 않도록)(룰북 [이름 겹침 정리](../game-rule/commands.md#이름-겹침-정리): 신통 이름은 명령어와 같게 짓지 않는다). (제안)
- 배우는 단계: 1 ~ 단계 수. **1성에 배우는 신통이 하나 이상** 있어야 한다(룰북: 1성에 첫 신통 하나 이상). (제안)
- 종류: `ATTACK` 공격 · `AREA_ATTACK` 범위 공격 · `DEFENSE` 방어 · `EVASION` 회피 · `HEALING` 치료 · `ESCAPE` 둔술 · `DETECTION` 탐지 · `STEALTH` 은신 · `CONCEALMENT` 렴기 · `BUFF` 보조(룰북 종류 그대로). (제안)
- 속성: 오행 0~5개, 또는 연체(`bodyRefining=true`, 이때 오행은 비어야 함). 룰북의 종류 '연체술 공격'(철권)은 `ATTACK` + `bodyRefining=true` 로 정의한다. (제안)
- 대상: `SELF` 자신 · `SINGLE` 한 대상 · `ALL_ENEMIES` 방의 모든 적(룰북). (제안)
- 소모: 스탯(`NONE` 없음 · `MANA` 법력 · `SENSE` 의식 · `ESSENCE` 정혈), 양(0 초과, 소수 첫째 자리까지, 없음이면 0), 틱마다 여부. 연체술 공법의 신통은 법력을 소모할 수 없다(룰북 [스탯 분류](../game-rule/stats.md#스탯-분류)). 은신처럼 '회복량의 1.5배' 같은 식으로 정하는 소모는 4차에 없다(신통 쓰기가 생길 때). (제안)
- 시전 시간 0~60초, 재사용 대기시간 0.1~3,600초(소수 첫째 자리까지. 룰북: 모든 신통에 있다). (제안)
- 쓸 수 있는 때: `COMBAT_ONLY` 전투 중만 · `ANYTIME` 전투 밖에도(룰북). (제안)
- **4차에 없는 항목:** 단계별 값(기본 위력·신통 계수·둔술 배율·은신/렴기 계수·지속 시간). 신통 쓰기·전투가 생길 때 더한다. (제안)
- 한 공법의 신통은 1~30개. (제안)

### 옥간·서책의 담긴 공법

- 종류가 `SCROLL`(옥간·서책)인 아이템 종류에 `담긴 공법`(공법 하나 또는 없음)을 더한다. 다른 종류에 두면 400이다. 한 공법을 여러 아이템 종류(옥간·서책 따로)에 담을 수 있다. 제작법을 담는 것은 제작이 생길 때 더한다. (제안)
- 담긴 공법은 언제든 바꿀 수 있다. 이미 누가 가진 그 옥간도 다음 `읽기` 부터 바뀐 공법을 담는다. 담긴 공법이 있는 아이템 종류의 종류를 바꾸려면 먼저 담긴 공법을 빼야 한다(400). 3차의 '쓰이는 물건의 종류 바꾸기 409' 는 그대로다. (제안)
- 공법이 담긴 아이템 종류가 있으면 그 공법을 지울 수 없다(409). 공법 쪽에서 세어 `technique → item` 의존을 만들지 않는다(2차 `FactionRepository.countZones` 관례). (제안)

### 저물탁

- 종류 `BAG` 의 이름을 `저물대·저물탁` 으로 바꾸고, 저물대 등급 `bagGrade` 에 저물탁 셋을 더한다: `BRACELET_LOW` 하급 저물탁 100칸 · `BRACELET_MIDDLE` 중급 200칸 · `BRACELET_HIGH` 상급 400칸(룰북). 기존 `LOW`·`MIDDLE`·`HIGH` 는 저물대다. 저물탁의 필요 경지(축기 초기)는 룰북이 정한 엔진 규칙이고 데이터로 입력받지 않는다. 기준가는 관리자가 넣는 콘텐츠다(룰북 하급 5,000 · 중급 15,000 · 상급 45,000). → [룰북: 저물대 · 저물탁](../game-rule/item.md#저물대--저물탁) (제안)
- 시작 소지품 검사에 저물탁 2개 이상 400 `저물탁은 하나까지만 찰 수 있습니다.` 를 더한다. 새 캐릭터는 범인이라 시작 소지품의 칸 검사에서 저물탁 칸은 0이다. (제안)
- 게임 규칙은 [명령어 처리: 저물탁](command.md#저물탁)에 있다.

### 캐릭터 경지 지정

- 관리자는 캐릭터의 경지를 경지 코드 하나로 지정한다(올리기·내리기·범인 모두). 수위·돌파·성공률을 거치지 않는다. 영근·익힌 공법·소지품은 바뀌지 않는다. (제안)
- 스탯은 새 경지 값으로 바로 계산되고 현재 수치도 다 찬다(경지 안정 기간 없음 — 룰북 안정 기간은 수위로 오를 때의 규칙이고 관리자 지정은 시험용 도구다). → [4차 이터레이션 열린 질문](index.md#4차-이터레이션-열린-질문) (제안)
- 관리 툴에서 영근·익힌 공법을 정하거나 바꾸는 기능은 두지 않는다. 공법은 게임에서 옥간으로 익힌다. (제안)

## 4차 화면

1~3차 화면에 더한다. 저장 전 클라이언트 검사는 하지 않고 서버 `detail` 을 보인다(1~3차 관례). (제안)

- 위쪽 공통 바: `시작 소지품` 옆에 `공법`, `캐릭터` 링크. (제안)
- `/techniques/` 공법 목록(이름·계열(`오행`/`연체술`)·속성(`목`, 없으면 `-`)·시작 경지·단계 수(`9성`)·신통 수·익힌 캐릭터 수)과 `공법 만들기` 링크(`/technique/`). (제안)
- `/technique/` (id 없음 = 새로, `/technique/?id=2` = 고치기): (제안)
  - `이름`, `묘사`(textarea), `속성`(체크박스 `금` `목` `수` `화` `토`, 안내 `속성을 고르지 않으면 연체술 공법입니다.`), `시작 경지`(선택, 범인 ~ 축기 대원만), `단계 수`(1~12, 바꾸면 단계 표 행이 늘거나 줄고 새 행은 모두 0).
  - 단계 표: 열 `단계`(`1성` …)·`필요 깨달음`(1성 칸은 입력 없이 `읽으면`)·`자질 조건`·`법력`·`의식`·`영력`·`정혈`·`육신`·`근력`·`영근 자질`.
  - 신통 표: 행마다 `이름`·`배우는 단계`(선택 `1성` ~)·`종류`·`속성`(체크박스 오행 + `연체`)·`대상`·`소모`(선택 `없음`/`법력`/`의식`/`정혈` + 양 + `틱마다` 체크)·`시전(초)`·`대기(초)`·`쓸 수 있는 때`(`전투 중만`/`전투 밖에도`)·`삭제`. `신통 추가` 의 새 행 기본값: 1성, 공격, 속성 없음, 한 대상, 소모 없음, 시전 0, 대기 3, 전투 중만.
  - `저장`, 고칠 때 `삭제`(확인 `'장춘공' 공법을 지울까요?`). 만들기에 성공하면 `/technique/?id=<새 id>` 로 간다.
  - 고칠 때 아래에 `이 공법이 담긴 물건`(이름 링크 → `/item/?id=`, 없으면 `없음`)과 `익힌 캐릭터 {n}명`.
- `/item/`: 종류가 `옥간·서책` 일 때만 `담긴 공법`(선택, 첫 항목 `없음` + 공법 이름순). 등급 선택은 종류가 `저물대·저물탁` 일 때 보이고 항목이 `하급 저물대 (20칸)` · `중급 저물대 (40칸)` · `상급 저물대 (80칸)` · `하급 저물탁 (100칸)` · `중급 저물탁 (200칸)` · `상급 저물탁 (400칸)` 이다. `/items/` 목록에 `담긴 공법` 열(없으면 `-`). (제안)
- `/characters/` 캐릭터 목록(이름·경지·영근(`목·화 진영근`, 없으면 `미정`)·익힌 공법 수·접속(`접속 중` 또는 `-`)), 이름 링크 → `/character/?id=`. (제안)
- `/character/?id=3`: 이름, 영근(읽기 전용 `목·화 진영근 (목 50, 화 50)`, 없으면 `아직 정하지 않음`), `경지`(선택) + `경지 지정` 버튼(확인 없이 바로 저장, 성공 `경지를 지정했습니다.`), 안내 `수위·돌파 없이 경지를 바로 바꿉니다. 스탯은 새 경지 값이 되고 바로 다 찹니다.`, 스탯 표(기혈·법력·의식·정혈·영력 최대치, 육신·근력, 저장 후 다시 그림), 익힌 공법 표(이름 링크 → `/technique/?id=`, `1/9성`, 없으면 `없음`). 다른 값은 고칠 수 없다. (제안)

## 4차 REST API

1차 D12 규칙(`/api/admin/**`, `ADMIN`, 변경에 `X-MUD-Client: 1`, `ProblemDetail`, 검증 실패·잘못된 값·없는 id 400, 이름 중복·규칙 충돌 409)을 그대로 따른다. 아래 전체가 (제안)이다.

| 메서드 · 경로 | 요청 | 응답 |
|---|---|---|
| `GET /api/admin/realms` | — | 200 `RealmResponse[]`(낮은 경지부터) |
| `GET /api/admin/techniques` | — | 200 `TechniqueSummaryResponse[]`(이름순) |
| `POST /api/admin/techniques` | `TechniqueSaveRequest` | 201 `TechniqueDetailResponse` |
| `GET /api/admin/techniques/{techniqueId}` | — | 200 `TechniqueDetailResponse` |
| `PUT /api/admin/techniques/{techniqueId}` | `TechniqueSaveRequest`(단계·신통은 통째로 바꿈) | 200 `TechniqueDetailResponse`. 익힌 캐릭터의 단계보다 단계 수를 줄이면 409 |
| `DELETE /api/admin/techniques/{techniqueId}` | — | 204. 익힌 캐릭터·담긴 물건이 있으면 409 |
| `POST /api/admin/item-types`, `PUT /api/admin/item-types/{itemTypeId}` | 3차 `ItemTypeSaveRequest` + `techniqueId`(number \| null, 빠지면 null = 담긴 공법 없음) | 3차와 같음 |
| `GET /api/admin/characters` | — | 200 `CharacterSummaryResponse[]`(이름순) |
| `GET /api/admin/characters/{characterId}` | — | 200 `CharacterDetailResponse` |
| `PUT /api/admin/characters/{characterId}/realm` | `{realm}` | 200 `CharacterDetailResponse` |

- 요청·응답 모양 (제안):
  - `RealmResponse {code, name}` — `code` 는 경지 enum 이름(`MORTAL`, `QI_1` … `QI_13`, `FOUNDATION_EARLY` · `FOUNDATION_MIDDLE` · `FOUNDATION_LATE` · `FOUNDATION_PEAK`), `name` 은 `범인`·`연기 1층`·`축기 초기` 같은 화면 이름.
  - `TechniqueSaveRequest {name, description, elements: string[], startRealm, stages: [{insightRequired, aptitudeRequired, manaBonus, senseBonus, spiritBonus, essenceBonus, bodyBonus, strengthBonus, aptitudeGain}], abilities: [{name, learnStage, kind, elements: string[], bodyRefining, target, costStat, costAmount, costPerTick, castSeconds, cooldownSeconds, usableWhen}]}` — `stages[0]` 이 1성이고 길이가 단계 수다. 숫자 칸이 빠지면 0, `elements` 가 빠지면 빈 목록이다.
  - `TechniqueSummaryResponse {id, name, elements, elementNames, lineName, startRealm, startRealmName, stageCount, abilityCount, learnerCount}` — `elementNames` 는 `목`·`화·토`(없으면 null), `lineName` 은 `오행`·`연체술`.
  - `TechniqueDetailResponse` = 저장 칸 전부 + `id, lineName, startRealmName, learnerCount, scrollItems: [{id, name}]`. 신통에 `kindName`, `targetName` 을 더한다.
  - `ItemTypeResponse` 에 `techniqueId, techniqueName`(없으면 null)을 더한다. `bagGradeName` 은 `하급 저물대`·`하급 저물탁` 처럼 저물대·저물탁을 붙인 이름이 된다.
  - `CharacterSummaryResponse {id, name, realm, realmName, spiritRootName, techniqueCount, online}` — `spiritRootName` 은 `목·화 진영근`(정하지 않았으면 null), `online` 은 지금 접속해 세계에 있는지(메모리 presence).
  - `CharacterDetailResponse {id, name, realm, realmName, spiritRoot: {name, roots: [{element, elementName, aptitude}]} | null, stats: {qiBlood, mana, sense, essence, spirit, body, strength}, techniques: [{id, name, stage, stageCount}]}` — `aptitude` 는 처음 자질 + 공법 증가(소수), `stats` 는 최대치(정수), `techniques` 는 익힌 순서.
- 예외 문구 (제안):

| 경우 | 상태 | `detail` |
|---|---|---|
| 공법 이름 규칙 | 400 | `공법 이름은 띄어쓰기 없이 1~12자로 정하십시오.` |
| 공법 이름 중복 | 409 | `이미 있는 공법 이름입니다: 장춘공` |

## 열린 질문

- 위 대상 가운데 각각 어디까지 관리 툴로 다루고 어디를 하드 코딩하는가? (예: 공법·신통의 효과)
- "배치" 는 방 하나에 두는 것인가, 구역을 정해 돌아다니게 하는 것까지 포함하는가? (룰북에는 특정 방에만 있거나 정해진 구역 안을 돌아다님) → [룰북: 몹](../game-rule/npc.md#몹) — 2차 NPC는 방 하나에 고정한다(창호, 2026-11-14). 돌아다니는 배치는 몹·이후 이터레이션에서 정한다. → [NPC: 생성과 배치](npc.md#생성과-배치)
- 관리 툴에서 바꾼 내용이 실행 중인 게임에 바로 반영되는가, 다시 시작해야 하는가? → (제안) 맵은 바로 반영된다. 2차의 성·종문·지역 소유·NPC와 3차의 아이템 종류·바닥 배치·시작 소지품·상점 역할도 바로 반영된다. 다른 콘텐츠는 그것이 생기는 이터레이션에서 정한다. → [관리 툴 변경의 반영](#관리-툴-변경의-반영)
- 관리자 사이에 권한 구분(예: 일부 기능만 쓰는 관리자)이 필요한가?
- 관리 툴에서 운영 기능(접속자 보기, 플레이어 캐릭터 수정 등)도 하는가? — 4차에 캐릭터 목록(접속 중 표시)과 경지 지정만 넣는다(제안). 그 밖의 캐릭터 수정은 열려 있다. → [4차 화면](#4차-화면)
