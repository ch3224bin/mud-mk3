## 실시간 통신과 월드 상태

- 게임 접속은 WebSocket으로 한다.
- 브라우저(play-client)가 world-server에 WebSocket으로 직접 연결한다.
- WebSocket으로 오가는 데이터는 JSON이다. 프론트엔드는 JSON을 받아 텍스트로 표현한다.
  - 메시지는 종류를 나타내는 `type` 을 가진 JSON이다: `{type, ...}` (예: `room`, `say`, `combat`, `system`, `prompt`).
  - 강조는 색 코드가 아니라 의미 정보로 보낸다(예: `tone`: `damage`, `npc`, `item`). 텍스트 모양과 테마는 프론트엔드가 정한다.
  - 1차의 메시지 목록과 스키마는 아래 [1차 WebSocket 메시지](#1차-websocket-메시지)에 (제안)으로 정했다. 2~5차 변경은 [2차](#2차-websocket-메시지-변경)·[3차](#3차-websocket-메시지-변경)·[4차](#4차-websocket-메시지-변경)·[5차](#5차-websocket-메시지-변경) 절에 있다. 5차 전투는 새 `type` 없이 `tone: "combat"` 을 쓴다. 신통·도주 등 이후 전투 메시지는 (미정).
- 월드 상태(방에 누가 있는지, 전투 등)는 메모리에 두고, 주기적으로 또는 중요한 시점에 DB에 저장한다.
- 저장 주기, 어떤 시점이 "중요한 시점" 인지, 틱은 (미정). 1차 값은 아래 [1차 월드 상태와 저장](#1차-월드-상태와-저장)에 있다. 4차 경지·영근·익힌 공법은 [4차 월드 상태와 저장](#4차-월드-상태와-저장)에 있다. 5차 서버 틱·몹·교전·현재 기혈은 [5차 월드 상태와 저장](#5차-월드-상태와-저장)에 있다.

### 1차 WebSocket 메시지

- 엔드포인트는 `ws://localhost:8080/ws/game` 이다. Spring raw WebSocket이고 STOMP는 쓰지 않는다. 인증은 핸드셰이크의 세션 쿠키로 한다. → [인증](auth.md#websocket-인증) (제안)
- 모든 메시지는 JSON이고 `type` 을 가진다. (제안)

클라이언트 → 서버 (제안)

| type | 필드 | 뜻 |
|---|---|---|
| `command` | `text` (최대 500자) | 입력 한 줄 |

서버 → 클라이언트 (제안)

| type | 필드 | 뜻 |
|---|---|---|
| `session` | `state`: `"creating"` \| `"playing"`, `characterName`: 문자열 \| null | 접속 상태가 바뀔 때 |
| `prompt` | `text` | 캐릭터 생성 중 묻는 말 |
| `room` | `zone`: `{id, name}`, `zoneEntered`: boolean, `room`: `{id, name, description}`, `exits`: 방위 한글 이름 목록(순서 `동 서 남 북 북동 북서 남동 남서 위 아래`), `occupants`: `[{name, kind:"player"}]`(나 빼고, 들어온 순서) | 방 보기 |
| `system` | `text`, `tone`: `"info"` \| `"error"` | 안내·결과·거절. `text` 에 줄바꿈(`\n`)이 있을 수 있다 |
| `notice` | `text`, `tone`: `"movement"`, `actor`, `event`: `"arrive"` \| `"leave"` \| `"appear"` \| `"disappear"` | 같은 방에서 일어난 일(남이 들어옴·나감·접속·접속 끊김) |
| `say` | `speaker`, `message`, `self`: boolean, `text`(그린 한 줄), `tone`: `"speech"` | 말하기 |
| `error` | `code`: `"AUTH_REQUIRED"` \| `"BAD_MESSAGE"`, `text` | 프로토콜 오류 |

- `tone` 은 의미 값이다. 1차에 쓰는 값은 `info`, `error`, `movement`, `speech` 다. 클라이언트는 `room` 을 그릴 때 `zone`(지역 줄)·`room-name`·`exits`·`occupant` 같은 자체 스타일 이름을 쓴다. (제안)
- 알 수 없는 메시지(JSON이 아니거나 `type` 이 모르는 값)와 바이너리 프레임은 `error` `BAD_MESSAGE` 로 답한다. (제안)
- 닫기 코드 (제안):

| 코드 | 뜻 |
|---|---|
| `1000` | `종료` 명령으로 정상 종료 |
| `1013` | 시작 방이 없어 세계가 열리지 않음 |
| `4401` | 로그인 안 됨(세션 없음·만료). 부채 정리 2차부터 연결 중에 HTTP 세션이 로그아웃·만료로 끝나도 이 코드로 닫는다([인증: WebSocket 인증](auth.md#websocket-인증)) |
| `4409` | 같은 계정이 다른 곳에서 접속해 밀려남 |
| `4500` | 이 연결로 못 보냄: 보류한 보내기가 512KB를 넘었거나 보내기에 실패 |

- 서버는 연결마다 보내기 줄(큐)을 두고 한 줄씩 보낸다. 느린 연결 하나가 게임 전체를 막지 않게 하려는 것이다. 보류가 512KB를 넘거나 보내기가 실패하면 그 연결만 4500으로 닫는다. (제안)
- 명령이 일으키는 출력(방 보기, 같은 방 알림 등)과 문구는 [명령어 처리](command.md#1차-명령어)에 있다.

### 2차 WebSocket 메시지 변경

1차 메시지에 더한다. 다른 메시지는 그대로다. (제안)

| type | 필드 | 뜻 |
|---|---|---|
| `room` | 1차 필드 + `owner`: `{kind: "castle" \| "sect", name}` \| `null`(지역 소유 없음). `occupants[].kind`: `"player"` \| `"npc"` | 방 보기 |
| `talk` | `npc`(NPC 이름), `word`(물은 낱말, 인사면 `null`), `text`(그린 줄들, `\n` 으로 나뉨), `tone`: `"talk"` | NPC 대답(묻는 사람에게만) |

- `occupants` 는 나를 뺀 플레이어(들어온 순서) 다음에 그 방에 배치된 NPC(만든 순서)를 `{name, kind: "npc"}` 로 둔다. 룰북 대상 목록 순서(플레이어 → 유니크 NPC)를 따른다. (제안)
- 새 `tone` 값은 `talk` 다. 클라이언트는 방의 NPC 줄에 자체 스타일 이름 `npc` 를, `talk` 의 줄들에 `talk` 를 쓴다. 소유는 방 이름 줄에 붙으므로 `room-name` 스타일을 그대로 쓴다. (제안)
- NPC가 방에 생기거나 사라져도(관리 변경) 같은 방 사람에게 알림 메시지는 없다. 다음 방 보기에 보인다. (제안)
- `대화` 명령의 문구는 [명령어 처리: 2차 명령어](command.md#2차-명령어)에 있다.

### 1차 월드 상태와 저장

- 메모리에 두는 것은 접속 중인 플레이어(캐릭터 id, 이름, 지금 방 id, 세션 id)와 WebSocket 세션 상태다. 메모리 저장소 구현은 `adapter/persistence/memory` 에 둔다. (제안)
- 맵(지역·방·출구)은 메모리에 캐시하지 않고 명령을 처리할 때마다 DB에서 읽는다. 그래서 관리 툴에서 바꾼 맵이 실행 중인 게임에 바로 반영된다. (제안) → [관리 툴](admin-tool.md#관리-툴-변경의-반영)
- 2차의 성·종문·지역 소유·NPC(대사·배치)도 메모리에 두지 않고 명령마다 DB에서 읽는다. NPC는 방에 고정되고 혼자 움직이지 않으므로 메모리 월드 상태에 넣지 않는다. (제안)
- 캐릭터 위치는 이동할 때마다 DB에 저장한다. 그래서 접속을 끊을 때 따로 저장할 것이 없다. 다시 접속하면 저장된 방에서 시작하고, 그 방이 지워졌으면 시작 방에서 시작한다. (제안)
- 플레이어가 서 있는 방을 관리자가 지우면 그 방의 캐릭터를 시작 방으로 옮긴다. 이 반영은 방 삭제가 커밋된 뒤(AFTER_COMMIT)에 게임에 적용된다. 접속 중이면 `system/info` `서 있던 곳이 사라져 시작 장소로 옮겨졌습니다.` 와 시작 방 `room` 을 보내고, 시작 방 사람들에게 `appear` 알림을 보낸다. 반영 전에 명령이 와도 현재 방이 없으면 그 자리에서 시작 방으로 옮긴다. (제안)
- 게임 명령 처리는 서버 전체에서 한 번에 하나로 직렬화한다(공정한 `ReentrantLock` 하나). 1차 사용자 수(소수)에는 충분하다. (제안)
- 같은 계정이 새로 접속하면 앞 연결에 `system/info` `다른 곳에서 접속해 이 연결을 끊습니다.` 를 보내고 4409로 닫는다. 캐릭터는 세계에 그대로 있고(나타난다·사라진다 알림 없음) 새 연결이 이어받아 지금 방 `room` 을 받는다. (제안)
- 틱과 주기 저장은 1차에 없다. (미정)
- 2차에도 서버 틱은 생기지 않는다. NPC가 알아서 말하기를 2차에 넣지 않아 NPC는 플레이어가 말을 걸 때만 답하기 때문이다(창호, 2026-11-14). → [2차 범위](index.md#2차-범위-npc-배치--기본-대화--성종문-정의)

### 3차 WebSocket 메시지 변경

3차(아이템)에 메시지가 늘어난다. 창호가 정했다(2026-11-14). 이름·필드·`tone` 은 구현에서 아래와 같이 정했다(2026-11-14). 1·2차에 더하고 다른 메시지는 그대로다. 아래 전체가 (제안)이다. → [이터레이션 계획: 3차 범위](index.md#3차-범위-아이템--영석--상점--저물대귀속--주기)

| type | 필드 | 뜻 |
|---|---|---|
| `room` | 2차 필드 + `items`: `[{name, count}]`(바닥 물건, 없으면 `[]`). JSON 필드 순서 `zone, zoneEntered, room, owner, exits, occupants, items` | 방 보기 |
| `inventory` | `usedSlots`, `totalSlots`, `stones`: `[{name, count}]`(가진 등급만, 하품부터), `items`: `[{name, count}]`(영석 밖, 표시 순서), `text`(그린 줄들, `\n`), `tone`: `"item"` | 소지품(묻는 사람에게만) |
| `system` | `tone` 에 `"item"` 을 더함 | 물건 명령의 결과(줍기·버리기·물건 보기·목록·사기·팔기·값·주기·받기·확인 질문). 거절은 그대로 `error`, `그만두었습니다.` 는 `info` |
| `notice` | `tone`: `"movement"` \| `"item"`, `event` 에 `"pick"` \| `"drop"` \| `"give"` 를 더함 | 같은 방 사람이 줍거나 버리거나 주고받음 |

- `room.items` 는 대상 목록의 맨 끝(룰북 방 보기 — 떨어진 물건)이다. 같은 종류는 한 줄로 묶는다. → [월드 구조: 3차 데이터 모델](world-structure.md#3차-데이터-모델) (제안)
- 새 `tone` 값은 `item`(강조는 의미 값이라는 위 원칙, 예 `item`)이다. 클라이언트 스타일 이름도 `item` 이다(바닥 물건 줄 포함). 물건 명령은 새 `type` 을 늘리지 않고 기존 `system` 에 `tone: "item"` 으로 보내고, 소지품만 구조를 가진 새 `type` `inventory` 로 보낸다. (제안)
- 명령 문구는 [명령어 처리: 3차 명령어](command.md#3차-명령어)에 있다.

### 3차 월드 상태와 저장

3차에 캐릭터의 소지품(물건·영석)과 방 바닥 물건이 상태로 생긴다. 창호가 정했다(2026-11-14). 저장·시간·동시성은 구현에서 아래와 같이 정했다. 아래 전체가 (제안)이다.

- **소지품 `Inventory`**(슬라이스 `inventory`, 캐릭터마다 하나, `character_id` 유일):
  - 칸 = 기본 2칸 + 가진 저물대 칸의 합. 저물대는 3개까지 가질 수 있고 칸을 차지하지 않는다. 그 밖의 물건은 `(종류)` 묶음마다 `올림(수 ÷ 겹침)` 칸이다(룰북의 '덜 찬 칸부터 채운다' 와 같은 결과). → [룰북: 저물대 · 저물탁](../game-rule/item.md#저물대--저물탁)
  - 칸이 모자랄 때(룰북): 줍기는 들어가는 만큼만, 사기·받기는 다 들어가지 않으면 하지 않는다. 저물대를 버리거나 팔거나 줘서 칸 합이 쓰는 칸보다 작아지면 하지 않는다. 저물대가 이미 3개면 더 얻지 못한다.
  - 소지품 묶음은 (캐릭터, 종류)마다 하나다(귀속 구분이 없어졌다). 묶음 유일은 도메인이 지키고 DB 유니크 제약은 두지 않는다(결제에서 하품을 다 내고 거스름 하품을 받는 것처럼 한 트랜잭션에서 같은 묶음을 비웠다 채울 때 일시 충돌을 피한다 — 2차 `npc_topic` 과 같은 까닭). 도메인은 바꿀 내용을 묶음별 증감으로 모아 한 번에 계산해 적용하고, 실패하면 아무것도 바꾸지 않는다.
  - 표시 순서(소지품 목록·이름 찾기): 영석(하품 → 극품) 다음 나머지를 얻은 순서(묶음이 처음 생긴 순서)다.
  - 테이블: `inventory`(UK `UK_INVENTORY_CHARACTER_ID`), `inventory_entry`(FK `inventory_id`·`item_type_id`). 2차 이전에 만든 캐릭터는 처음 볼 때 빈 소지품으로 시작한다.
- **저장 시점: 소지품이 바뀌는 명령의 트랜잭션에서 바로 DB에 쓴다**(1차 '캐릭터 위치는 이동할 때마다' 와 같은 방식). 메모리에 두지 않는다. 물건이 오가는 것은 두 쪽이 함께 바뀌어야 하는 중요한 시점이기 때문이다. 그래서 접속을 끊을 때 따로 저장할 것이 없다. (제안)
- **바닥 물건은 PostgreSQL에 둔다**(관리자 배치·버린 물건 모두, 서버를 다시 시작해도 남음). 버린 물건의 5분과 배치의 재등장은 서버 틱·예약 작업 없이 **바닥을 읽을 때 현재 시각과 비교**해 처리한다. 그래서 3차에도 서버 틱은 생기지 않는다. → [월드 구조: 3차 데이터 모델](world-structure.md#3차-데이터-모델) (제안)
- **시계:** `support/config/ClockConfig` 의 `Clock` 빈(`Clock.systemUTC()`)을 시간이 필요한 서비스(바닥, 확인 대기, 아이템 종류 지우기)가 주입받는다. 테스트는 `@Primary` `MutableClock`(고정 시각에서 `advance(Duration)`)으로 바꾼다. 새 의존성은 없다. (제안)
- **동시성·트랜잭션:** 게임 명령은 1차대로 서버 전체 게임 락 하나로 직렬화되고, 락 안에서 명령마다 트랜잭션 하나를 열고 닫는다. (제안)
  - 같은 바닥 물건을 둘이 동시에 주워도 한 사람씩 처리되고, 뒤 사람은 앞 사람이 커밋한 남은 수를 읽는다.
  - 주기는 받는 사람이 그 순간 같은 방에 접속해 있는지(메모리 presence)와 두 소지품 변경을 한 명령 안에서 처리한다. 상대가 나가거나 끊는 처리도 같은 락을 지나므로 '주는 중에 나감' 이 끼어들 수 없다. 끊긴 뒤라면 `여기에 한립은 없습니다.` 이고 물건은 그대로다.
  - 사기·팔기·주기·줍기·버리기는 검사를 다 한 뒤에 바꾼다(도메인 메서드가 실패하면 아무것도 바꾸지 않는다). 줍기는 먼저 줍는 수를 정한 뒤 바닥에서 덜고 소지품에 넣어 두 쪽 수가 어긋나지 않게 한다. 커밋이 실패하면 메시지를 보내지 않는다(1차 outbox).
  - 관리 요청은 게임 락 밖이다. 관리자 배치 수정과 게임 줍기가 겹치면 나중 커밋이 이긴다(관리 수정은 남은 수를 처음 수로 되돌리는 동작이라 받아들임 — 2차 동시 편집 경합과 같은 판정). 쓰이는 아이템 종류 지우기 경합은 FK 가 막고 409 다. 관리자가 배치를 지우는 커밋과 게임 줍기가 겹쳐 게임 쪽이 지워진 행을 고치면 그 명령은 예외로 롤백된다(드묾, 1·2차 드문 경합과 같이 받아들임).
- 영석 심기는 `ApplicationReadyEvent` 에서 한다(빈 DB 첫 기동 직후 아주 짧은 틈은 받아들임). → [관리 툴: 영석](admin-tool.md#영석) (제안)
- 아이템 종류·바닥 배치·시작 소지품·상점 역할도 메모리에 두지 않고 명령마다 DB에서 읽는다. → [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영) (제안)

### 4차 WebSocket 메시지 변경

4차(경지·스탯·공법 배우기)에 더한다. 범위는 고나가 창호 원문을 해석한 것이고 창호 확인함 (2026-11-15). 1~3차에 더하고 다른 메시지는 그대로다. 아래 전체가 (제안)이다. → [이터레이션 계획: 4차 범위](index.md#4차-범위-경지스탯--임의-경지-상승--공법신통-배우기)

| type | 필드 | 뜻 |
|---|---|---|
| `status` | `characterName`, `realm`: `{code, name}`, `spiritRoot`: `{name, roots: [{element, elementName, aptitude}]}`(오행 순, `aptitude` 는 소수점 버린 정수), `stats`: `{qiBlood, mana, sense, essence, spirit}` 마다 `{current, max}` + `body`, `strength`(정수), `cultivation`: `{current, required}` \| `null`(범인), `text`(그린 줄들, `\n`), `tone`: `"status"` | `상태`(묻는 사람에게만) |
| `system` | `tone` 에 `"growth"` 를 더함 | `읽기` 성공, 관리 툴 경지 지정 알림 |
| `session` | 그대로. 영근을 정하지 않은 기존 캐릭터도 영근을 고르는 동안 `state: "creating"`, `characterName` 은 그 이름 | 접속 상태 |

- `공법`·`신통` 은 새 `type` 없이 `system` `tone: "info"` 여러 줄이다. 구조가 필요한 상태 창을 둘 때를 위해 `상태` 만 구조를 가진 `status` 로 보낸다(3차 `inventory` 와 같은 판단). 4차 play-client는 `status.text` 를 로그에 그리고 늘 보이는 상태 창은 두지 않는다. (제안)
- 새 `tone` 값은 `status`·`growth` 다. 클라이언트 스타일 이름도 같다. (제안)
- 명령 문구는 [명령어 처리: 4차 명령어](command.md#4차-명령어)에 있다.

### 4차 월드 상태와 저장

4차에 캐릭터의 경지·영근·익힌 공법이 상태로 생긴다. 범위는 고나가 창호 원문을 해석한 것이고 창호 확인함 (2026-11-15). 아래 전체가 (제안)이다.

- **저장하는 것**(PostgreSQL, 바뀌는 명령·관리 요청의 트랜잭션에서 바로 쓴다 — 3차 소지품과 같은 방식):
  - 캐릭터의 경지(`player_character.realm`, `varchar(32)` enum 문자열, **orm.xml 에서 `nullable="true"`** 로 매핑해 `ddl-auto=update` 가 기존 행이 있는 표에 열을 더할 수 있게 한다 — `not null` 열을 더하면 행이 있는 PostgreSQL에서 실패해 서버가 뜨지 않는다). 새 캐릭터는 `MORTAL`(범인, 룰북). 서버가 뜰 때(`ApplicationReadyEvent`, `LegacySchemaCleaner` 다음·영석 심기 앞 — 구현은 두 `ApplicationReadyEvent` 리스너에 `@Order(0)`(경지 채우기)·`@Order(10)`(영석 심기)을 붙여 순서를 고정한다) `realm IS NULL` 인 행을 `QI_1`(연기 1층)로 한 번에 바꾼다. 도메인은 null을 받지 않는다(채우기 전 아주 짧은 틈은 영석 심기와 같이 받아들인다). H2·PostgreSQL 둘 다 동작해야 한다. → [4차 이터레이션 열린 질문](index.md#4차-이터레이션-열린-질문)
  - 영근: 캐릭터마다 오행과 처음 자질(소수, 100 ÷ 개수 — 룰북 [영근 · 영근 자질](../game-rule/stats.md#영근--영근-자질)). 행이 없으면 '아직 정하지 않음' 이고 접속 때 고르게 한다 → [명령어 처리: 캐릭터 생성 · 영근](command.md#캐릭터-생성--영근-4차).
  - 익힌 공법: (캐릭터, 공법)마다 하나, 지금 단계(4차에는 늘 1)와 익힌 순서. (캐릭터, 공법) 유일.
- **저장하지 않고 계산하는 것:** 스탯 최대치·포인트 스탯·영근 자질·배운 신통은 명령마다 경지와 익힌 공법의 정의로 계산한다. 그래서 관리 툴에서 공법 정의를 고치면 익힌 캐릭터에게도 다음 명령부터 반영된다. → [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영)
  - 육신 = 경지 육신 + 공법 육신. 근력 = 경지 근력 + 공법 근력. 영력 최대치 = 경지 영력 + 공법 영력. 의식·정혈 최대치 = 경지 값 + 공법 값. 기혈 최대치 = 육신 × 10. 법력 최대치 = 영력 현재 수치 × 5 + 공법 법력(영력 현재 수치가 0이면 0). 영근 자질 = 처음 자질 + 공법 영근 자질 증가(공법 속성 영근에). '공법 X' 는 익힌 공법마다 1성부터 지금 단계까지 스탯 증가의 합이다. 정혈 비율은 늘 100%다. → 룰북 [기혈](../game-rule/stats.md#기혈), [법력](../game-rule/stats.md#법력), [정혈](../game-rule/stats.md#정혈)
  - **현재 수치는 저장하지 않는다.** 4차에는 현재 수치를 깎는 것(전투·신통·소모·사망)이 없고, 룰북 [최대치가 바뀔 때](../game-rule/stats.md#최대치가-바뀔-때) 규칙(오르면 함께 오름, 내려가면 깎임)을 지키면 현재 수치는 늘 최대치이기 때문이다. 화면·`status` 의 `current` 는 최대치와 같다. 현재 수치 저장은 깎는 것이 생기는 이터레이션(5차 전투)에 더하고, 그때 기존 캐릭터는 가득 찬 값으로 시작한다.
  - 경지 안정 기간(영력이 차오르는 시간)은 4차에 없다. 관리 툴 지정과 입문은 영력도 바로 찬다. → [4차 이터레이션 열린 질문](index.md#4차-이터레이션-열린-질문)
  - 깨달음·수위는 4차에 쌓는 길이 없어 저장하지 않고 0으로 보인다. → [명령어 처리: 상태](command.md#상태)
- **소지품 칸과 저물탁:** 칸 = 기본 2칸 + 저물대 칸 합 + (경지가 축기 초기 이상이면) 저물탁 칸. `inventory` 슬라이스는 경지를 알지 않고 '저물탁을 열 수 있는가' 를 인자로 받는다(`inventory → character` 의존을 만들지 않음). 관리 툴로 경지를 내려 칸이 쓰는 칸보다 작아질 수 있고, 그때 남은 칸은 0으로 본다. → [명령어 처리: 저물탁](command.md#저물탁)
- **관리 툴 경지 지정의 반영:** 관리 요청은 게임 락 밖에서 경지를 커밋하고, 커밋 뒤(AFTER_COMMIT, 1차 방 삭제 반영과 같은 방식) 게임 쪽이 접속 중인 그 캐릭터에게 알림을 보낸다. 경지는 메모리에 두지 않고 명령마다 DB에서 읽으므로 반영 전에 온 명령도 새 경지를 본다. 이동·경지는 열 하나만 쓰는 쿼리라(엔티티 저장은 그 열을 쓰지 않음) 관리 지정과 게임 이동이 겹쳐도 서로 되돌리지 않는다. 같은 열(경지)을 관리 지정과 게임 `읽기`(범인 → 연기 1층)가 함께 쓰면 나중 커밋이 이긴다(드묾, 받아들임). (제안)
- 공법·신통 정의도 메모리에 두지 않고 명령마다 DB에서 읽는다.
- 4차에도 서버 틱은 생기지 않는다(경지 안정 기간·자연 회복이 없다). 5차에 생긴다 → [서버 틱](#서버-틱).

#### 경지 몫 스탯 표

### 5차 월드 상태와 저장

5차에 몹·교전·시체가 메모리 월드 상태로 생기고, 플레이어의 현재 기혈을 저장한다. 창호가 정했다(2026-11-15). 아래 전체가 (제안)이다.

- **DB에 두는 것:** 몹 유형·드롭 표·배치(관리 툴 데이터 → [관리 툴: 5차 데이터](admin-tool.md#5차-데이터)), 플레이어의 **깎인 기혈**(`player_character.qi_blood_lost`, `double precision`, nullable — 4차 `realm` 처럼 행이 있는 표에 열을 더할 수 있게 하고, null은 0 = 가득 참). 현재 기혈 = 기혈 최대치 − 깎인 기혈(0 아래로 내려가지 않음, 화면은 버린 정수).
  - 현재 수치 대신 깎인 양을 두는 까닭: 기혈 최대치는 경지·공법 정의로 계산되므로(4차) 최대치가 오를 때 현재 수치도 오른 만큼 오른다는 룰북 [최대치가 바뀔 때](../game-rule/stats.md#최대치가-바뀔-때) 규칙이 저절로 지켜진다. 관리 툴 경지 지정으로 최대치가 내려가면 같은 트랜잭션에서 깎인 기혈을 내려간 만큼 줄여(0 아래 없음) '현재 수치가 새 최대치보다 높으면 새 최대치까지 깎임' 을 지킨다. 공법 정의를 고쳐 최대치가 내려가는 경우는 맞추지 않는다(드묾, 받아들임).
  - 쓰는 때: 맞을 때마다·질 때·다 찰 때, 그 틱·명령의 트랜잭션에서 바로 쓴다(3차 소지품과 같은 '바뀌는 트랜잭션에서 바로' 방식). 그래서 접속을 끊을 때 따로 저장할 것이 없다.
  - **이 열만 쓰는 전용 쿼리로만 읽고 쓴다.** 엔티티 매핑은 이 열을 읽기 전용(`insertable=false`, `updatable=false`)으로 두어 엔티티 저장이 이 열을 쓰지 않고, 틱의 기혈 쓰기는 `update player_character set qi_blood_lost = … where id = …` 하나로 다른 열을 쓰지 않는다. 이동·경지도 열 하나만 쓰는 쿼리라(debt-1) 1초마다 맞는 쓰기·관리 툴 경지 지정·게임 이동이 서로를 옛 값으로 되돌리지 않는다. 관리 경지 지정이 깎인 기혈을 줄이는 쓰기와 같은 순간의 틱 쓰기만 나중 커밋이 이긴다(그 열 하나, 드묾, 받아들임). (제안)
  - 4차 L4의 '현재 수치 열' 가운데 5차에 깎이는 것은 기혈뿐이라 기혈만 더한다. 법력·의식·정혈 현재 수치는 계속 저장하지 않고 늘 최대치다.
- **메모리에만 두는 것**(서버를 다시 시작하면 사라짐): 살아 있는 몹(배치마다 수만큼, 나타날 때 읽은 스탯·현재 기혈·교전 상대 목록·위협·피해 기록·다음 행동 시각·다시 찰 시각·재등장 시각), 플레이어의 교전 상태(교전 상대 목록·노리는 상대·다음 공격 시각·다시 찰 시각), 시체(처치자·쓰러진 시각·남은 드롭). 다시 시작하면 첫 틱에 배치대로 몹이 다 찬 채 나타나고, 시체·교전은 없다(플레이어의 깎인 기혈은 DB에 남아 다음 접속 10초 뒤 찬다).
  - 접속하지 않은 캐릭터의 교전·대기시간 기록은 교전 상대가 없고 다음 공격 시각·대기시간이 모두 지나면 틱이 지운다. 방을 지우면 그 방의 시체·몹도 바로 지운다. (제안)
  - 코드 배치는 [코딩 규칙: 아키텍처](../../../.claude/rules/architecture.md#메모리-월드-상태)대로: 개념은 `domain/combat`, 저장 포트는 `application/game/required`, 메모리 구현은 `adapter/persistence/memory`(1차 `InMemoryPresenceRepository` 와 같음). (제안)
- **동시성:** 틱도 명령처럼 서버 전체 게임 락 하나로 직렬화되고, 락 안에서 틱마다 트랜잭션 하나를 열고 닫는다(1차 방식). 그래서 명령과 틱의 행동이 섞이지 않고, 한 행동의 결과가 다 반영된 뒤 다음 것이 처리된다(룰북 [처리 순서](../game-rule/combat.md#처리-순서)). 보낼 메시지는 커밋 뒤 보낸다(1차 outbox). 커밋이 실패하면 메모리 상태는 되돌리지 않는다(1차 한계). (제안)
- **시계와 난수:** 교전 시각은 3차 `Clock` 빈으로 잰다. 드롭 굴림은 `support/config` 의 `RandomGenerator` 빈으로 하고, 테스트는 정해진 수를 내는 가짜로 바꾼다(`MutableClock` 과 같은 방식). 새 의존성은 없다. (제안)
  - 드롭 굴림이 난수를 쓰는 순서(테스트가 이 순서로 수를 정한다): 고정 재료(난수 없음) → 고정 재료가 있으면 영석 확률(30%)에 실수 하나, 걸리면 개수에 실수 하나 → 계층마다(고급 → 희귀 → 진귀, 목록이 비지 않은 계층만) 나머지 확률에 실수 하나, 개수마다 목록에서 고르는 정수 하나. 난수는 게임 락 안에서만 쓴다. (제안)
  - 몹의 피해 기록은 상대가 교전에서 빠져도(나갔거나 져서) 몹이 다시 차기·쓰러짐·재등장 하기 전까지 남아 처치자 계산에 들어간다(룰북 처치 귀속: 나갔거나 졌어도 귀속 그대로, 다 찰 때 기록을 지움). 그 상대가 다시 교전하면 이어 쓴다. 플레이어가 다시 교전하면 예약된 기혈 채우기는 취소된다. 처치자는 쓰러질 때 정해 둔다. (제안)
- 관리 툴의 몹·배치 변경 반영은 [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영)에 있다.

#### 서버 틱

5차에 처음으로 서버 틱이 생긴다. (제안)

- 주기는 룰북 틱 1초다(룰북 [처리 순서](../game-rule/combat.md#처리-순서)). Spring 스케줄링(`@Scheduled`, 1초 고정 간격)이 어댑터에서 게임 쪽 provided 포트의 `tick()` 을 부른다. 설정 `mud.game.tick-enabled`(기본 `true`)로 끌 수 있고, 테스트는 끄고 `tick()` 을 직접 부른다(시계는 `MutableClock`). (제안)
- 한 틱의 순서: (제안)
  1. **배치 맞추기:** DB의 몹 배치를 읽어 메모리의 몹과 맞춘다(새 배치는 나타나게, 바뀌거나 없어진 배치는 지움). → [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영)
  2. **행동:** 다음 행동(공격) 시각이 지금 이전인 플레이어·몹의 행동을 시각이 이른 순서(같으면 교전을 먼저 시작한 쪽)로 하나씩 처리한다. 쓰러진 쪽의 남은 행동은 취소된다. 행동한 뒤 다음 시각은 '그 행동의 시각 + 3초' 이고, 그것도 이미 지났으면 지나지 않은 때까지 3초씩 더한다(밀린 행동을 몰아서 하지 않음).
  3. **다시 차기:** 교전 상대가 모두 사라진 지 10초가 된 몹은 기혈이 다 차고 위협·피해 기록을 지운다(룰북 [몹 스탯](../game-rule/npc.md#몹-스탯)). 플레이어는 [교전 뒤 기혈](command.md#교전-뒤-기혈) 규칙대로 찬다.
  4. **시체 사라짐:** 쓰러진 지 3분이 된 시체를 지운다(알리지 않음).
  5. **재등장:** 쓰러진 지 재등장 시간이 된 몹을 같은 방에 기혈이 다 찬 채 나타나게 한다(그 방에 `청모랑이 나타난다.`).
- 구현 세부 (제안):
  - 행동 정렬 키는 (행동 시각, 교전 시작 순번)이다. 교전 시작 순번은 교전하지 않던 쪽이 교전에 들어갈 때 늘어나는 번호이고, 같은 시각이면 교전 시작 순번이 낮은 쪽이 먼저 처리된다. 플레이어와 몹이 함께 교전에 들어가면 플레이어가 낮은 번호를 받아 먼저 행동하고, 이미 다른 이와 싸우는 몹에 뒤늦게 끼어든 플레이어는 더 높은 번호를 받는다. 행동 직전에 다시 확인한다(세계에 있음·같은 방·서로 교전 중·몹이 살아 있음). 이 틱에 쓰러진 쪽의 남은 행동은 여기서 떨어진다.
  - 스케줄러에서 틱 처리가 예외를 내면 로그(`log.error`)만 남기고 다음 틱을 막지 않는다. 스케줄러는 `mud.game.tick-enabled` 가 `true`(없으면 `true`)일 때만 뜬다.
  - 테스트는 스케줄러를 끄고(`mud.game.tick-enabled: false`) 시계(`MutableClock`)를 움직인 뒤 `tick()` 을 직접 부른다. 실제로 기다리지 않는다.
- 룰북 틱 처리 순서(회복 → 틱 소모 → 지속 피해 → 판정 → 끝내기)의 항목은 5차에 하나도 없다(자연 회복·틱 소모·지속 피해·기절이 없음). 생기면 위 2 앞뒤에 끼운다. (제안)
- 피해로 기혈이 0이 되는 판정은 틱을 기다리지 않고 그 행동 안에서 한다(룰북). (제안)
- 아무도 접속하지 않아도 틱은 돈다(재등장·다시 차기). 틱마다 배치를 읽는 쿼리 하나와 트랜잭션 하나가 든다(단일 월드·소수 플레이어라 받아들임). (제안)

### 6차 WebSocket 메시지 변경

6차(공격 신통 쓰기 + 깨달음 쌓기)에 더한다. 창호가 정했다(2026-11-15). 1~5차에 더하고 다른 메시지는 그대로다. 새 `type` 과 새 `tone` 은 없다. 아래 전체가 (제안)이다. → [이터레이션 계획: 6차 범위](index.md#6차-범위-공격-신통-쓰기--깨달음-쌓기)

| type | 필드 | 뜻 |
|---|---|---|
| `status` | `stats.mana.current` 가 저장된 현재 법력이 된다(5차까지는 늘 최대치). `insight`: `[{kind, name, amount}]` 를 더함 — `kind` 는 `METAL`·`WOOD`·`WATER`·`FIRE`·`EARTH`·`BODY`, `name` 은 `금`·`목`·`수`·`화`·`토`·`연체`, `amount` 는 소수점 버린 정수, 여섯 개가 늘 이 순서. `text` 의 깨달음 줄도 쌓인 값이 된다 | `상태` |

| `notice` | 그대로. 신통으로 교전이 시작되면 5차 `engage`, 신통으로 쓰러뜨리면 5차 `kill` | 같은 방 다른 사람에게 |

- 6차 play-client는 `status.insight` 를 쓰지 않고 `text` 를 그린다(늘 보이는 상태 창이 생길 때를 위한 구조, 4차 판단과 같음). 배운 신통·재사용 대기를 구조로 보내는 메시지는 없다(자동완성에 신통 이름을 넣을 때 더함). (제안)
- 명령 문구는 [명령어 처리: 6차 명령어](command.md#6차-명령어)에 있다.

### 6차 월드 상태와 저장

6차에 플레이어의 현재 법력·깨달음을 저장하고, 대기시간·시전을 메모리에 둔다. 창호가 정했다(2026-11-15). 아래 전체가 (제안)이다.

- **DB에 두는 것:**
  - **깎인 법력** `player_character.mana_lost`(`double precision`, nullable, null은 0 = 가득 참). 현재 법력 = 법력 최대치 − 깎인 법력(0 아래로 내려가지 않음, 화면은 버린 정수). 5차 [깎인 기혈](#5차-월드-상태와-저장)과 같은 방식이다: 엔티티는 이 열을 읽기 전용으로 매핑하고 이 열만 쓰는 전용 쿼리로 읽고 쓴다(캐릭터 행 저장이 이 열을 되돌리지 않음). 관리 툴 경지 지정으로 법력 최대치가 내려가면 같은 트랜잭션에서 깎인 법력을 내려간 만큼 줄인다(0 아래 없음). 공법 정의를 고쳐 최대치가 내려가는 경우는 맞추지 않는다(5차와 같음, 드묾). 그때 깎인 법력이 최대치를 넘어도 회복 틱은 보이는 현재 법력(0)에서 채워 쓴다(넘는 몫을 먼저 먹지 않음).
    - 쓰는 때: 신통이 발동할 때(그 명령·틱의 트랜잭션), 법력 회복 틱(깎인 법력이 0보다 큰 접속 중 캐릭터만, 그 틱의 트랜잭션), 관리 경지 지정. 접속을 끊을 때 따로 저장할 것이 없다.
    - 회복 틱은 회복할 캐릭터마다 1초에 쓰기 하나가 든다(단일 월드·소수 플레이어라 받아들임, 5차 틱 쿼리와 같은 판단). 늘면 메모리에 두고 모아 쓰는 쪽으로 바꾼다.
    - 영력 현재 수치는 6차에도 저장하지 않는다(늘 최대치). 영력을 깎는 무리한 사용을 6차는 거절하기 때문이다 → [명령어 처리: 신통 쓰기](command.md#신통-쓰기). 의식·정혈 현재 수치도 계속 저장하지 않는다.
  - **깨달음** `character_insight`(캐릭터 id, `kind` enum 문자열 `METAL`·`WOOD`·`WATER`·`FIRE`·`EARTH`·`BODY`, `amount` `double precision`), (캐릭터, `kind`) 유일. 행이 없으면 0. 신통이 발동하는 트랜잭션에서 바로 더한다(그 행을 찾아 값을 더해 저장하고(dirty checking), 없으면 행을 만든다. 일괄 갱신 쿼리는 쓰지 않는다). `kind` 열은 `varchar(16)` 이다. 캐릭터 행과 다른 표라 관리 경지 지정·이동과 겹쳐 되돌리는 일이 없다. 연체는 오행 `Element` 가 아니라서 깨달음 갈래 enum을 따로 둔다.
  - **관리 데이터:** 공격 신통의 단계별 값 `ability_stage_power`(신통 id, 단계, 기본 위력 `numeric(7,2)`, 계수 `numeric(6,3)`), 이펙트 문장 `ability_effect_line`(신통 id, 순서, 글 `varchar(100)`). 4차 신통처럼 공법 저장 때 통째로 바뀐다 → [관리 툴: 6차 데이터](admin-tool.md#6차-데이터). 두 표 모두 순서를 지키는 `position` 열을 갖는다(한 신통이 값 컬렉션을 둘 가질 때 순서 없는 묶음이 둘이 되지 않게 하려고 위 열 목록에 하나 더함). 단계별 값은 저장할 때 기본 위력 소수 둘째 자리·계수 셋째 자리로 맞추므로 응답이 `2.00`·`1.200` 으로 나온다. 신통 이펙트 문장 열은 `varchar(100)` 이고 비어 있지 않다. (제안)
- **메모리에만 두는 것**(서버를 다시 시작하면 사라짐): 캐릭터마다 공통 대기시간이 끝나는 시각, (공법 id, 신통 이름)마다 재사용 대기시간이 끝나는 시각, 시전(신통, 대상 몹, 발동 시각), 교전(플레이어, 몹)마다 깨달음 한 상대 상한의 남은 양과 알렸는지(상한은 몹 쪽에 두고 플레이어 id 로 센다). 상한은 그 플레이어가 교전에서 빠질 때·몹이 쓰러질 때·다시 찰 때·다시 나타날 때 지우고, 쓰러질 때의 지우기는 그 신통의 깨달음을 쌓은 뒤에 한다. 대기시간은 끝나는 시각으로 두므로 세계에서 사라져도 남아 흐른다(룰북 [접속 종료](../game-rule/combat.md#접속-종료): 재사용 대기시간은 접속을 끊은 동안에도 흐름). 시전은 세계에서 사라질 때·질 때 지운다. 깨달음 상한은 그 교전이 끝날 때 지운다.
  - 코드 배치는 5차대로: 개념은 `domain/combat`(대기시간·시전·위력·피해), 깨달음 계산(`InsightKind`·`CharacterInsight`·`Insight`·`InsightGain`)은 `domain/cultivation` 의 순수 계산이다. 새 의존 `combat → cultivation` 을 허용한다(순환 없음 — `cultivation` 은 `combat` 을 쓰지 않음). 저장 포트는 `application/game/required`, 메모리 구현은 `adapter/persistence/memory`. (제안)
- **위력·피해 계산의 자리:** 위력 → 받는 쪽 배율 → 육신 층 → 기혈 순서를 한 곳에서 계산하고, 받는 쪽 배율은 6차에 늘 ×1 을 돌려주는 자리로 둔다. 상성(창호: 나중)과 룰북 귀물·음혼 속성 배율은 이 자리에 붙인다. 5차 임시 `공격`·몹 공격도 같은 계산을 지난다. 구현은 받는 쪽 배율을 곱한 값(층을 거치기 전 피해)을 위협·피해 기록에 더하고, 층을 지난 값(`afterLayers`)으로 기혈을 깎는다. 5차 공격·몹 공격은 속성 없는 공격(`AttackNature.NONE`)으로 이 자리를 지난다. (제안) → [룰북: 피해 흐름](../game-rule/combat.md#피해-흐름)
- **시계와 난수:** 대기시간·시전은 3차 `Clock` 으로 잰다. 이펙트 문장 고르기는 5차 `RandomGenerator` 빈으로 한다. 난수 순서(테스트가 이 순서로 수를 정한다): 신통이 발동할 때 문장이 2개 이상이면 문장을 고르는 정수 하나(1개면 쓰지 않음) → 그 신통으로 몹이 쓰러지면 5차 드롭 굴림 순서. 난수는 게임 락 안에서만 쓴다.
- **동시성:** 신통 명령·시전 발동·회복은 5차처럼 서버 전체 게임 락 하나로 직렬화된다. 보낼 메시지는 커밋 뒤 보낸다(1차 outbox).
- **서버 틱 변경**(5차 [서버 틱](#서버-틱)의 순서에 끼움):
  1. 배치 맞추기(5차)
  2. **법력 회복:** 접속해 세계에 있는 캐릭터마다 법력 최대치 × 0.5%(영기 농도 보통) × 지난 초(0~1초로 자름)를 채운다(룰북 처리 순서 1 '회복'). → [명령어 처리: 법력 회복](command.md#법력-회복)
  3. 행동(5차): 다음 공격 시각이 된 플레이어·몹의 자동 공격과 **발동 시각이 된 시전**을 같은 정렬 키(시각, 교전 시작 순번)로 처리한다. 아직 교전하지 않은 캐릭터의 시전은 같은 시각의 교전 중인 행동 뒤에, 시전을 시작한 순서대로 처리한다(정렬 키는 (시각, 무리, 순번, 종류), 같은 시각·순번이면 자동 공격이 먼저 — [명령어 처리: 시전과 `중지`](command.md#시전과-중지)). 방이 지워져 시작 방으로 옮겨진 캐릭터의 시전은 남겨 발동 때 흩어지게 한다. 발동 직전에 다시 확인한다 → [명령어 처리: 시전과 `중지`](command.md#시전과-중지)
  4. 다시 차기·시체 사라짐·재등장(5차). 몹이 다시 차거나 쓰러지면 그 몹과의 깨달음 상한도 지운다(교전이 끝났으므로).
- 관리 툴의 신통 정의 변경 반영은 [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영)에 있다.

### 부채 정리 2차 WebSocket 메시지 변경

부채 정리 2차(2026-11-18)에 1~6차 메시지에 더한다. 새 `type`·`tone`·`error` `code` 는 없다. → [이터레이션 계획: 부채 정리 2차](index.md#부채-정리-2차-debt-2)

| type | 필드 | 뜻 |
|---|---|---|
| `room` | `quiet`: boolean 을 더함. 방 보기는 `false`, 조용한 방 상태는 `true`(그때 `zoneEntered` 는 늘 `false`) | `quiet: true` 는 화면에 그리지 않고 자동완성 후보만 바꾸는 바뀐 방 상태(창호 결정 (2026-11-18)) → [명령어 처리: 방 상태 조용히 보내기](command.md#방-상태-조용히-보내기) |
| `error` | 그대로(`AUTH_REQUIRED`). 로그아웃·세션 만료 때도 보낸 뒤 4401 로 닫는다 | → [인증: WebSocket 인증](auth.md#websocket-인증) |

- 조용한 방 상태를 새 `type` 으로 두지 않고 `room` 에 `quiet` 를 단 것은, 필드가 방 보기와 같고 받는 쪽 후보 규칙도 같아서다. (제안)
- 메시지를 만드는 곳(서버 `GameMessage.RoomMessage`)에 칸이 하나 늘 뿐 직렬화 방식은 그대로다. (제안)

### 관리 툴 삭제 월드 상태

관리 툴 삭제(2026-11-20)에 캐릭터 삭제가 메모리 월드 상태를 함께 정리한다. 새 WebSocket 메시지는 없다. 결정은 고나 판단 (2026-11-20, 창호 위임)이고 → [관리 툴: 캐릭터 삭제](admin-tool.md#캐릭터-삭제), 아래 세부는 (제안)이다.

- **캐릭터 id 를 들고 있는 메모리 구조**와 삭제 때 하는 일:

| 구조 | 들고 있는 것 | 캐릭터 삭제 때 |
|---|---|---|
| 게임 연결 상태(`GameService` 의 연결 id → `GameSession`) | 계정 id, 캐릭터 id, 확인 대기 | 그 계정의 연결이 있으면 접속 중이라 거절(409) |
| 접속 기록 `PresenceRepository`(`OnlinePlayer`) | 캐릭터 id·방·연결 id | 있으면 접속 중이라 거절(409). 게임 연결이 없으면 없다 |
| 교전 기록 `PlayerCombatRepository`(`PlayerCombat`) | 교전 상대 몹·다음 공격·다시 차기·법력 회복 시각 | 지운다(끊긴 뒤 틱이 지우기 전까지 남아 있을 수 있음) |
| 대기시간·시전 `AbilityTimersRepository`(`AbilityTimers`) | 공통·재사용 대기시간, 시전 | 지운다(대기시간은 끊긴 뒤에도 흐르므로 남아 있을 수 있음) |
| 몹 `MobInstanceRepository`(`MobInstance`) | 교전 상대·끝난 상대의 위협·피해 기록, 노리는 대상, 깨달음 한 상대 상한·알림 | 모든 몹에서 그 캐릭터의 기록(끝난 상대의 위협·피해 기록, 깨달음 상한·알림)을 지우고, 대상이면 비운다. 교전 상대에서는 연결이 끊길 때 이미 빠졌으므로 다시 차기 예약은 바뀌지 않는다 |
| 시체 `CorpseRepository`(`Corpse`) | 처치자 id(60초 독점 수습) | 그대로 둔다(id 가 다시 쓰이지 않아 아무도 독점하지 못할 뿐, 60초 뒤엔 누구나 수습) |
| 조용한 방 표시 `RoomRefresher` | 방 id 만 | 상관없음 |

- **순서:** 게임 락을 잡고 트랜잭션 하나를 연다 → 캐릭터를 찾고(없으면 400) 접속 중이면 409 → DB 행을 지움 → 위 표대로 메모리를 정리 → 커밋. 커밋이 실패하면 1차 한계대로 메모리는 되돌리지 않는다(접속하지 않은 캐릭터의 교전·대기 기록이 사라질 뿐이라 받아들임). (제안)
- **몹 삭제**는 메모리를 바로 건드리지 않는다. 다음 틱의 배치 맞추기가 5차 배치 삭제와 같이 몹을 지운다 → [관리 툴: 몹 삭제](admin-tool.md#몹-삭제). (제안)

## 저장소 구성

mud-mk3 저장소 아래 모듈 3개로 나뉜다. 모듈 이름은 역할이 드러나게 지었다(`backend`·`frontend` 같은 이름은 쓰지 않음).

| 모듈 | 역할 | 기술 |
|---|---|---|
| `world-server` | 게임 서버. 월드 상태, 명령 처리, 데이터 저장. play-client와는 WebSocket, admin-console과는 REST로 통신 | Java Spring |
| `play-client` | 플레이 화면 | Next.js |
| `admin-console` | 관리 툴. play-client와 따로 분리된 앱 → [관리 툴](admin-tool.md) | Next.js |

- world-server의 루트 패키지는 `mudmk3` 다. 애그리거트(슬라이스)는 `zone`, `room`, `world`, `account`, `character`, `game`(메모리 월드)이다. (제안)
- 슬라이스 의존은 `room → zone`, `world → room`, `character → world`, `character → account`, `game → character, room, world` 이고 순환은 없다. `character → account` 는 캐릭터를 만들 때 계정이 있는지 확인하려는 의존이다. (제안)
- 2차에 슬라이스 `faction`(성·종문), `npc` 를 더했다. 의존은 `zone → faction`, `room → zone`, `world → room`, `npc → room`, `character → world, account, npc`, `game → character, room, world, npc` 이고 순환은 없다. `character → npc` 는 캐릭터 이름이 NPC 이름과 겹치는지 보려는 의존이다. 성·종문의 소유 지역 수는 `faction` 쪽에서 세어 `faction → zone` 의존을 만들지 않는다. (제안)
- 3차에 슬라이스 `item`(아이템 종류·영석·결제 계산), `inventory`(소지품), `floor`(방 바닥 물건)를 더했다(각각 domain·application). 의존은 `inventory → item, world`, `floor → item, room`, `npc → item, room`, `world → item, room`, `character → inventory`(+2차), `game → inventory, floor, item, npc`(+2차)이고 순환은 없다. `item` 은 아무 슬라이스도 쓰지 않는다. 쓰이는 아이템 종류인지는 `ItemTypeRepository` 의 JPQL로 센다(2차 `FactionRepository.countZones` 관례). (제안)
- 3차 테이블(`ddl-auto=update`, 마이그레이션 도구 없음): `item_type`(UK `UK_ITEM_TYPE_NAME`, `UK_ITEM_TYPE_SPIRIT_STONE_GRADE`), `inventory`, `inventory_entry`, `floor_placement`(FK `item_type_id`, `room_id` FK 없음), `dropped_item`(같음), `npc.shop_kind` 열, `npc_shop_item`(`position` 순서 열, `item_type_id` FK 없음), `world_starting_item`(`position` 순서 열, `item_type_id` FK 없음). enum 열(`item_type.category`·`bag_grade`·`spirit_stone_grade`, `npc.shop_kind`)은 1·2차 관례대로 문자열(`STRING`, `varchar(N)`)로 저장한다. 바닥 시각 열은 `timestamp with time zone` 이다. `귀속`·`거래 가능` 삭제(창호, 2026-11-14)로 엔티티에서 옛 열을 뺐다. 이미 만들어진 DB의 옛 열 정리 방식은 [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영)에 한 곳에만 적는다. (제안)
- 4차에 슬라이스 `technique`(공법·신통 정의)를 더하고, 경지·영근은 `character` 에, 익힌 공법과 스탯 계산은 새 슬라이스 `cultivation` 에 둔다(제안). 의존은 `item → technique`(옥간·서책의 담긴 공법), `cultivation → character, technique, item, inventory`, `game → cultivation, technique`(+3차)이고 순환은 없다. `technique` 은 아무 슬라이스도 쓰지 않는다. `Realm`·`Element` 는 슬라이스가 아니라 `domain/shared` 에 둔다(`technique`·`character` 가 함께 씀). `game` 슬라이스는 관리 REST가 캐릭터의 접속 여부를 보도록 provided 포트 `PresenceFinder` 를 둔다(메모리 presence를 게임 락 없이 읽음). 공법을 익힌 캐릭터 수와 담긴 아이템 종류 수는 `TechniqueRepository` 의 JPQL로 센다(`FactionRepository.countZones` 관례). 4차 테이블(`ddl-auto=update`): `technique`(UK 이름), `technique_element`, `technique_stage`(순서 열), `ability`(순서 열), `ability_element`, `character_spirit_root`, `character_technique`(UK (캐릭터, 공법)) — 둘 다 FK `character_id` → `player_character.id`, `player_character.realm` 열(nullable, 위 채우기), `item_type.technique_id` 열(FK). enum 열은 1~3차 관례대로 문자열이다. (제안)
- 5차에 슬라이스 `mob`(몹 유형·드롭 표·배치, domain·application)과 도메인 슬라이스 `combat`(살아 있는 몹·플레이어 교전 상태·시체 — 메모리 월드 상태의 개념)을 더한다(제안). 의존은 `mob → item, room`, `combat → mob`, `game → mob, combat`(+4차)이고 순환은 없다. 드롭 표에 든 아이템 종류 수는 `ItemTypeRepository` 의 JPQL로 센다(`item → mob` 의존을 만들지 않음, `FactionRepository.countZones` 관례). 서버 틱을 부르는 스케줄러는 어댑터 `adapter/scheduling` 에 둔다. 5차 테이블(`ddl-auto=update`): `mob_type`(UK 이름), `mob_fixed_drop`(순서 열), `mob_tier_drop`(순서 열), `mob_placement`(`room_id` FK 없음), `player_character.qi_blood_lost` 열(nullable). enum 열은 1~4차 관례대로 문자열이다. (제안)
- 6차에 새 슬라이스는 없다. 개념은 `technique`(단계별 값·이펙트 문장 검사·렌더)·`character`(깎인 법력)·`cultivation`(깨달음)·`combat`(대기시간·시전·위력)에 나뉘고, 새 의존은 `combat → cultivation`(깨달음 계산)이다. 순환은 없다. 6차 테이블(`ddl-auto=update`): `ability_stage_power`·`ability_effect_line`(둘 다 `position` 열)·`character_insight`(UK (캐릭터, `kind`), `kind` 는 `varchar(16)` enum)과 `player_character.mana_lost` 열(nullable). enum 열의 PostgreSQL CHECK 는 서버가 뜰 때 `LegacySchemaCleaner` 가 Hibernate 가 만든 enum CHECK 를 모두 지운다(값 검사는 Java enum 매핑이 한다, [관리 툴: 관리 툴 변경의 반영](admin-tool.md#관리-툴-변경의-반영)). 서버가 뜰 때 기존 신통의 비어 있는 이펙트 문장·단계별 값을 채운다(`@Order(20)`, [관리 툴: 기존 신통 채우기](admin-tool.md#기존-신통-채우기)). (제안)
- 이 구조와 메모리 저장소 구현 위치는 [코딩 규칙: 아키텍처](../../../.claude/rules/architecture.md)를 따른다.

## 플레이 화면 (play-client)

- 터미널형 화면이다: 스크롤되는 출력 로그 + 아래쪽 입력창.
- 입력창에서 ↑↓ 로 명령 히스토리를 오가고, 탭으로 자동완성한다(명령어, 대상 이름).
- 정적 클라이언트로 만든다. SSR 없이 Next.js 정적 export·클라이언트 위주로 쓴다.
- 방 보기 화면은 `room` 메시지를 아래 모양으로 그린다. 룰북 방 보기 순서에서 1차에 있는 것만 둔다. → [룰북: 방 보기](../game-rule/world.md#방-보기) (제안)

```
◇ 청석숲            ← zoneEntered일 때만
청석숲 오솔길
늙은 소나무 사이로 좁은 길이 굽어 있다.
출구: 북 남동        ← 출구 없으면 "출구: 없음"
한립                ← occupants 한 줄에 하나
```

- 2차 방 보기 (제안): 지역 소유가 있으면 방 이름 줄 뒤에 두 칸 띄우고 `[소유 이름]` 을 붙인다(룰북 `청석숲 오솔길  (영기: 보통)` 처럼 방 이름 줄에 덧붙이는 모양). NPC 줄은 플레이어 줄 다음에 오고 플레이어 줄과 다른 색(스타일 `npc`)으로 그린다. `talk` 메시지는 `text` 를 줄로 나눠 스타일 `talk` 로 그린다. (제안)

```
◇ 청석숲                 ← zoneEntered일 때만 (1차와 같음)
청석성 남문  [청석성]     ← owner 있을 때만 "  [이름]"
돌로 쌓은 성문이 우뚝 서 있다.
출구: 북 남
한립                     ← occupant player (스타일 occupant)
왕씨                     ← occupant npc (스타일 npc)
```
- 3차 방 보기 (제안): NPC 줄 다음에 바닥 물건 줄을 그린다(스타일 `item`, 색 `.line-item` `#9fd4a3`). 수가 2 이상이면 `이름 N개`, 1이면 이름만 그린다(룰북 예). `inventory` 는 `text` 를 줄로 나눠 스타일 `item` 으로 그리고, `system`·`notice` 의 `tone: "item"` 도 스타일 `item` 이다. 자동완성 명령 목록과 이름 후보는 [명령어 처리: 3차 도움말](command.md#3차-도움말)에 있다.

```
청석숲 오솔길
늙은 소나무 사이로 좁은 길이 굽어 있다.
출구: 북 남동
한립                     ← occupant player
왕씨                     ← occupant npc
하품 영석 3개             ← 바닥 물건 (스타일 item)
연기기 비검
```
- 4차 (제안): `status` 는 `text` 를 줄로 나눠 스타일 `status` 로, `system` 의 `tone: "growth"` 는 스타일 `growth` 로 그린다. 색은 `status` `#c8d3f5`(`.line-status`), `growth` `#f0c674`(`.line-growth`) 다. 늘 보이는 상태 창은 두지 않는다. 자동완성 명령 목록과 이름 후보는 [명령어 처리: 4차 도움말](command.md#4차-도움말)에 있다.
- 5차 (제안): 방 보기에서 NPC 줄 다음에 몹 줄, 그다음 시체 줄, 그다음 바닥 물건 줄을 그린다(모양은 [명령어 처리: 교전 메시지](command.md#교전-메시지)). 몹·시체 줄은 스타일 `mob`(색 `#e5a46b`, `.line-mob`), `system`·`notice` 의 `tone: "combat"` 은 스타일 `combat`(색 `#f28b82`, `.line-combat`)이다. 자동완성 명령 목록과 이름 후보는 [명령어 처리: 5차 도움말](command.md#5차-도움말)에 있다.
- 부채 정리 2차 (제안): `room` 의 `quiet: true` 는 그리지 않고 이름 후보만 바꾼다([명령어 처리: 방 상태 조용히 보내기](command.md#방-상태-조용히-보내기)). Tab 의 여러 낱말 이름은 이름 전체를 채운다([명령어 처리: 여러 낱말 이름 자동완성](command.md#여러-낱말-이름-자동완성)). 4401 로 닫히면 지금처럼 로그인 화면으로 가고, 닫히기 전에 받은 `error` `AUTH_REQUIRED` 의 `text` 를 로그인 화면 버튼 위에 한 줄(스타일 muted, `role="status"`)로 보인다(받은 것이 없으면 보이지 않음). `로그아웃` 버튼으로 나가는 동안 4401 로 닫히면 안내 없이 로그인 화면으로 간다(로그아웃 응답이 실패해도 그사이 4401 이 왔으면 세션이 끝난 것으로 본다). → [인증: WebSocket 인증](auth.md#websocket-인증)
- world-server가 보낸 JSON 메시지를 `type`·`tone` 에 따라 텍스트로 그린다. → [실시간 통신과 월드 상태](#실시간-통신과-월드-상태)

## 관리 툴 (admin-console)

- play-client와 분리된 Next.js 앱이다.
- world-server와 REST로 통신한다.
- play-client처럼 정적 export로 만든다(SSR 없음). 경로는 id를 쿼리스트링으로 받는다. → [관리 툴: 1차 화면](admin-tool.md#1차-화면) (제안)

## 배포

- Dockerfile은 모듈마다 둔다. (제안)
  - world-server: JDK 이미지로 빌드하고 JRE 이미지로 실행한다.
  - play-client·admin-console: node 이미지로 정적 export를 빌드하고 nginx가 정적 파일만 서빙한다.
- 저장소 루트 `compose.yaml` 이 `postgres`, `world-server`, `play-client`, `admin-console` 을 띄운다. 처음에는 맥북에서 docker-compose로 운영해 본다. (제안)
  - 포트: world-server `8080`, play-client `3000`, admin-console `3001`(컨테이너 안은 nginx `80`), PostgreSQL `5432`(루트 compose에서는 밖으로 열지 않음). 브라우저가 world-server에 직접 붙고 프록시는 없다. (제안)
  - 프론트의 `NEXT_PUBLIC_*` 값은 빌드 때 박히므로 compose `build.args` 로 넘긴다. (제안)
  - `world-server/compose.yaml` 은 `./gradlew bootRun`(`local` 프로필) 개발 때 DB만 띄우는 용도다(`spring-boot-docker-compose`). 루트 compose와 별개다. (제안)
  - 1차 스키마는 `spring.jpa.hibernate.ddl-auto=update`(운영), 테스트는 기본 `create-drop` 이다. 마이그레이션 도구(Flyway)는 첫 실제 배포 전에 들인다(debt-1 판단). (제안)
- 환경변수 (제안):

| 이름 | 쓰는 곳 | 기본값 · 예 |
|---|---|---|
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | world-server | 없으면 `not-configured` 로 떠서 앱은 뜨지만 Google 로그인은 실패한다(개발용 로그인은 됨). 시작할 때 경고 로그 |
| `MUD_ADMIN_EMAILS` | world-server | 쉼표로 나눈 목록(예: `a@example.com,b@example.com`) |
| `MUD_PLAY_CLIENT_URL`, `MUD_ADMIN_CONSOLE_URL` | world-server(로그인 뒤 돌아갈 곳) | `http://localhost:3000/`, `http://localhost:3001/` |
| `MUD_CORS_ALLOWED_ORIGINS` | world-server(REST CORS + WebSocket Origin) | `http://localhost:3000,http://localhost:3001` |
| `MUD_DEV_LOGIN_ENABLED` | world-server(`local` 프로필에서만 의미) | `false` |
| `SPRING_PROFILES_ACTIVE` | world-server | 비움(운영) / `local` |
| `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` | world-server | compose: `jdbc:postgresql://postgres:5432/mud`, `mud`, `${POSTGRES_PASSWORD}` |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | postgres | `mud`, `mud`, 루트 `.env` 에서 읽음(비면 compose가 실패) |
| `NEXT_PUBLIC_WORLD_SERVER_URL` | 두 클라이언트(빌드 때) | `http://localhost:8080` (WebSocket 주소는 `http` 를 `ws` 로 바꿔 `/ws/game` 을 붙임) |
| `NEXT_PUBLIC_DEV_LOGIN` | 두 클라이언트(빌드 때) | `false` (compose에서는 `MUD_DEV_LOGIN_ENABLED` 값을 넘김) |

- 추후 Kubernetes 환경으로 배포한다. 시기와 구성은 (미정).
