# 월드 구조

월드·존·인스턴스(비경). → [목차](index.md)

존은 룰북의 [지역](../game-rule/world.md#지역)과 같은 것이다. 이 문서에서는 '존(지역)' 으로 쓴다.

게임 규칙(방이 가지는 것, 출구, 이동, 전송진, 게임 시간)은 [룰북: 세계와 이동](../game-rule/world.md), 비경 규칙은 [룰북: 비경 탐사](../game-rule/game-structure.md#비경-탐사)를 따른다.

## 계층

| 단위 | 설명 | 룰북 용어 |
|---|---|---|
| 월드 | 게임 세계 전체. 하나만 운영한다. → [플랫폼](platform.md#단일-월드) | — |
| 존 | 월드를 나누는 단위. 방들을 묶는다 | [지역](../game-rule/world.md#지역) (같은 것) |
| 인스턴스 | 비경 | [비경](../game-rule/game-structure.md#비경-탐사) |

- 존(지역)·인스턴스를 이루는 가장 작은 단위는 룰북의 [장소(방)](../game-rule/world.md#장소)다.
- 맵(존(지역)·방·출구)과 비경은 관리 툴에서 만든다. → [관리 툴](admin-tool.md)
- 1차 이터레이션: 관리 툴에서 맵(방·출구)을 만들고 게임에서 돌아다니기까지. → [이터레이션 계획](index.md#이터레이션-계획)

## 성 · 종문 소유

- 어떤 맵은 어떤 성 또는 종문의 것이다. 모든 맵이 성이나 종문 소유인 것은 아니다.
- 소유는 존(지역) 단위로 정한다. 지역 하나가 통째로 한 성 또는 종문의 소유가 된다.
  - 창호가 말한 '문파' 는 룰북의 [종문](../game-rule/game-structure.md#종문)이다(용어집: 종문 = 룰북의 옛 표현 '문파').
- 성·종문은 관리 툴에서 맵보다 먼저 정의되어야 한다. → [관리 툴](admin-tool.md#관리-화면에서-하는-일)
- 2차의 성·종문은 이름과 묘사만 가진다. 지역 소유는 게임 방 화면 머리에 보인다(예: `[청석성]`). (창호, 2026-11-14)
- 성·종문 정의와 맵의 소유 지정은 2차 이터레이션에서 한다. 관련 열린 질문은 [2차 이터레이션 열린 질문](index.md#2차-이터레이션-열린-질문)에 있다. → [이터레이션 계획](index.md#이터레이션-계획)
- 성·종문 규칙은 [룰북: 성](../game-rule/game-structure.md#성), [룰북: 종문](../game-rule/game-structure.md#종문)을 따른다.

### 2차 데이터 모델

- 성·종문 `Faction`: 종류(`성` / `종문`), 이름(1~30자, 앞뒤 공백 자름), 묘사(0~500자). 성과 종문은 종류만 다르고 같은 틀이다. 이름은 **성과 종문을 통틀어 유일**하다(방 머리 `[청석성]` 이 무엇을 가리키는지 헷갈리지 않게). 2차에 가입·퀘스트·안전 장소 같은 규칙은 없다. (제안)
- 지역 소유: 존(지역) `Zone` 에 소유(성·종문 하나 또는 없음)를 더한다. 관리 툴에서 지역을 만들거나 고칠 때 정한다. (제안)
- 지우기 규칙: **소유한 지역이 있는 성·종문은 지울 수 없다**(`소유한 지역이 있는 성·종문은 지울 수 없습니다`). 지역의 소유를 `없음` 이나 다른 성·종문으로 바꾼 뒤에는 지울 수 있다. (제안)
- 성·종문의 이름을 바꾸거나 지역 소유를 바꾸면 그 지역 방 머리 표시가 다음 방 보기부터 바뀐다(같은 방 사람에게 따로 알리지 않음). (제안)
- 방 머리 그림은 [플랫폼: 플레이 화면](platform.md#플레이-화면-play-client), 관리 화면·REST API는 [관리 툴: 2차 화면](admin-tool.md#2차-화면)에 있다.

## 방 바닥 물건

- 3차(아이템)에 방 바닥에 물건이 놓인다. 창호가 정했다(2026-11-14). → [이터레이션 계획: 3차 범위](index.md#3차-범위-아이템--영석--상점--저물대귀속--주기)
- 바닥 물건은 두 가지로 생긴다.
  - 관리 툴에서 방에 배치한 물건. → [관리 툴: 3차 범위](admin-tool.md#3차-범위)
  - 플레이어가 `버리기` 로 버린 물건. 룰북은 5분 동안 남고 그동안 누구든 주울 수 있으며 5분이 지나면 사라진다고 정했다. → [룰북: 줍기와 버리기](../game-rule/item.md#줍기와-버리기)
- 바닥 물건은 방 보기의 대상 목록 맨 끝(떨어진 물건)에 보인다. → [룰북: 방 보기](../game-rule/world.md#방-보기)
- 배치한 물건을 주운 뒤 다시 나타나는지, 서버를 다시 시작하면 바닥 물건이 남는지, 저장을 어떻게 하는지는 3차 구현에서 아래 [3차 데이터 모델](#3차-데이터-모델)과 같이 정했다. → [3차 이터레이션 열린 질문](index.md#3차-이터레이션-열린-질문), [플랫폼: 3차 월드 상태와 저장](platform.md#3차-월드-상태와-저장)

### 3차 데이터 모델

구현했다(2026-11-14). 아래 전체가 (제안)이다. 슬라이스는 `floor` 다. 배치와 버린 물건 모두 PostgreSQL에 두어 서버를 다시 시작해도 남는다.

- **관리자 배치** `FloorPlacement`: 방(`room_id`, 방 FK 없음 — NPC와 같은 까닭), 아이템 종류, 수(1~9,999), 재등장(분, 1~1,440 또는 없음), 남은 수, 비워진 시각. 모두가 함께 쓰는 하나다(캐릭터마다가 아님). 줍는 만큼 남은 수가 줄고, 0이 된 시각부터 재등장 분이 지나면 처음 수로 다시 놓인다. 재등장이 없으면 한 번뿐이다(관리자가 다시 고치면 처음 수로 돌아간다). 룰북은 버린 물건만 정했다. 모두 한 번인 MUD 관례에 재등장을 고를 수 있게 했고, 유니크 NPC 재등장 기본 10분을 관리 화면 기본값으로 썼다. → [룰북: NPC](../game-rule/npc.md) (제안)
- **버린 물건** `DroppedItem`: 방, 아이템 종류, 수, 사라지는 시각(버린 시각 + 5분). 그동안 누구든 줍는다(룰북). 같은 물건을 또 버리면 따로 5분을 잰다. 관리자는 퀘스트 물건·영석도 바닥에 둘 수 있다. → [룰북: 줍기와 버리기](../game-rule/item.md#줍기와-버리기) (제안)
- **시간 재기(서버 틱 없음):** 바닥을 읽을 때(방 보기·줍기·보기) 그 방에서 사라질 시각이 지난 버린 물건을 지우고, 재등장할 때가 된 배치를 채운다. 그래서 예약 작업·스케줄러를 두지 않는다. 아무도 다시 보지 않는 방의 지난 행은 남지만 보이지 않는다. 시각은 주입한 `Clock` 으로 잰다. → [플랫폼: 3차 월드 상태와 저장](platform.md#3차-월드-상태와-저장) (제안)
- 시각 열은 Hibernate 기본인 `timestamp with time zone` 이다(계획은 `timestamp`). (제안)
- 방을 지우면 그 방의 배치·버린 물건도 같은 트랜잭션에서 지운다(2차 `RoomDeletedEvent` 동기 리스너 관례). (제안)
- **방 보기의 바닥 물건:** `room` 메시지에 `items: [{name, count}]` 를 더한다. 대상 목록 맨 끝(룰북 방 보기 — 떨어진 물건)이다. 같은 종류는 배치·버린 것을 합쳐 한 줄로 묶고, 순서는 그 종류가 처음 나온 자리(배치 id 순 → 버린 것 id 순)다. 그 시각에 0인 배치와 사라진 버린 물건은 묶기 전에 뺀다. 그리는 모양은 수가 2 이상이면 `하품 영석 3개`, 1이면 `연기기 비검`(룰북 예 그대로)이다. 바닥이 바뀌어도 같은 방 사람의 방 보기를 다시 보내지 않고 [같은 방 알림](command.md#3차-같은-방-알림)만 보낸다. → [룰북: 방 보기](../game-rule/world.md#방-보기), [플랫폼: 3차 WebSocket 메시지 변경](platform.md#3차-websocket-메시지-변경) (제안)
- 관리 화면·REST API는 [관리 툴: 3차 화면](admin-tool.md#3차-화면), [관리 툴: 3차 REST API](admin-tool.md#3차-rest-api)에 있다.

## 1차 데이터 모델

- 존(지역) `Zone`: 이름(1~30자, 유일), 분위기 묘사(0~500자). (제안)
- 방 `Room`: 지역 하나, 이름(1~30자), 묘사(1~1000자), 출구 목록. (제안)
- 출구 `Exit`: 방위(룰북의 10방위: 동 서 남 북 북동 북서 남동 남서 위 아래)와 대상 방. 한 방에 같은 방위 출구는 하나다. 자기 자신으로 가는 출구는 막는다. 이름 있는 출구·비밀문은 다음 이터레이션이다. → [룰북: 출구](../game-rule/world.md#출구) (제안)
- 추후: 출구는 정해진 방위(10방위) 외에 특수한 출구가 있을 수 있다. 형태는 정하지 않았다. → [열린 질문](#열린-질문)
  - 1차 구현 메모: 출구는 별도 엔티티(`room_exit` 테이블, 자체 id)라 열·필드를 더하는 것은 막히지 않는다. 다만 지금은 방위가 필수(`direction` NOT NULL)이고 `(room_id, direction)` 유일 제약이 있으며, 이동 명령(`Command.Move`)·출구 응답(`ExitResponse`)·방 화면이 방위만 전제하므로 특수 출구를 넣을 때 이 부분을 같이 바꿔야 한다.
- 반대 방향 출구는 관리 툴에서 요청할 때 같이 만든다. → [관리 툴: 출구 만들기·지우기 규칙](admin-tool.md#출구-만들기지우기-규칙) (제안)
- 세계 설정 `WorldSettings`(행 하나): 시작 방. 관리자가 지정한다. 시작 방은 지울 수 없다. 시작 방이 없으면 게임에 들어갈 수 없다. (제안) → [플랫폼: 1차 WebSocket 메시지](platform.md#1차-websocket-메시지)
- 지우기 규칙: 방이 있는 지역은 지울 수 없다. 방을 지우면 그 방으로 오는 출구도 같이 지운다. 시작 방은 지울 수 없다. (제안)
- 계정 `Account`: Google `sub`(유일), 이메일. 캐릭터 `PlayerCharacter`: 계정 id(유일 = 계정당 1개), 이름(유일), 현재 방 id. (제안)
- 1차 스키마는 `spring.jpa.hibernate.ddl-auto=update`(운영), 테스트는 기본 `create-drop` 이다. 마이그레이션 도구(Flyway)는 다음 이터레이션이다. (제안)
- 시작 방이 없을 때 게임에 들어가려 하면 `system/error` `아직 세계가 열리지 않았습니다. 관리자가 시작 방을 정해야 합니다.` 를 보내고 1013으로 닫는다. (제안)
